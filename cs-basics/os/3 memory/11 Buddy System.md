# Buddy System

## 伙伴系统简介

**伙伴系统**（Buddy System），是一种经典的内存管理算法，主要用于**操作系统内核或底层内存分配器中**，比如 Linux 内核中的物理内存管理（页框分配器）就使用了伙伴系统的思想。它主要用于**管理固定大小的块（通常是 2 的幂次方大小），并高效地处理内存的分配与回收，同时减少外部碎片**。

在伙伴系统中：

-  内存被划分为**大小固定的块**，通常是 **2^k 个页（比如 1页、2页、4页、8页...）**。
-  当申请一块内存时，系统会尝试分配**最接近且不小于请求大小的最小 2^k 块**。
-  如果当前大小的块**不够（已全部分配）**，系统会尝试**向上一级更大的块（2^(k+1)）申请**，然后将该大块**一分为二（buddy 分裂）**，得到两个 2^k 的块，其中一个用于分配，另一个作为伙伴保留。
-  当某个块被释放时，系统会检查它的“伙伴块”（地址相邻、大小相同的块）是否也空闲。如果是，则将两个伙伴**合并为一个更大的块（2^(k+1)）**，以便后续分配使用。

## 核心原理

**内存块划分**

-   以**页（通常4KB）**为最小单位，将空闲内存划分为不同阶（order）的块，每块大小为 $2^{order}$ 页（如1页、2页、4页……最大4MB）。
-   通过free_area[]数组管理11个阶（0~10）的空闲块链表，每个链表存储对应大小的空闲内存块。

**伙伴关系**

两个大小相同、物理地址连续的内存块互为“伙伴”，释放时可合并为更大的块。合并条件包括：
-   大小相同且均为空闲；
-   地址满足 $\text{address} \mod 2^{order+1} = 0$。

## 工作流程

**内存分配**

-   若申请大小为 $2^n$ 页，优先从free_area[n]链表中分配；若无空闲块，则向上查找更大阶的块并递归拆分。
-   示例：申请3页时，实际分配4页（$2^2$），导致1页内部碎片。

**内存释放**

-   释放的块会检查其伙伴是否空闲，若满足条件则合并为更高阶的块，并递归尝试进一步合并。

## 问题一：申请内存不够时会怎么办？

>   ✅ 情况描述：

当应用程序或内核模块**申请某大小的内存（比如需要一个 2^k 大小的块）时，如果当前空闲链表中**没有可用的该大小的块，伙伴系统会尝试向更大的块进行分裂。

>   🔄 具体流程：

1. **查找所需大小的空闲块（比如 2^k）**

  -  首先在对应大小的空闲链表（free list）中查找是否有可用的 2^k 块。
  -  **如果有**：直接分配，完成。

2. **如果没有可用的 2^k 块**

  -  伙伴系统会尝试查找**更大的块，比如 2^(k+1)**。
  -  如果存在空闲的 2^(k+1) 块：
     -  **将该块一分为二，生成两个 2^k 的块**；
     -  其中一个块**分配出去**，另一个作为伙伴块**放回空闲链表**。
  -  如果 2^(k+1) 也没有：
     -  继续向更上一级（$2^{(k+2)}$、$2^{(k+3)}$...）查找，直到找到某个大小的空闲块为止；
     -  然后**逐级向下分裂**，直到得到所需的 2^k 块。

3. **如果所有更大的块也都已分配完（即没有足够大的块可分裂）**，此时，伙伴系统将无法满足本次内存申请请求，分配失败！

-   如果申请某个大小的块时，伙伴系统中没有可用块，并且通过分裂更大的块也无法得到（即所有上级块也都已分配），那么这次内存申请就会失败。
-   若默认迁移类型（如可移动页）的空闲块不足，伙伴系统会尝试从其他迁移类型（如可回收、不可移动）的空闲链表中分配，通过 __rmqueue_fallback 函数实现。
-   若后备迁移类型仍无足够内存，触发直接内存回收或唤醒 kswapd 线程异步回收缓存和匿名页。
-   在操作系统内核中，这通常意味着：

    -  **内存不足（Out of Memory, OOM）**
    -  调用者可能收到 **NULL 指针、错误码（如 -ENOMEM）、或触发 OOM Killer（Linux）** 来终止某些进程以释放内存。

>   回收后仍不足的可能原因与处理

碎片化问题

-   外部碎片：即使回收了内存，若空闲块不连续（如伙伴块被占用），无法合并为大块，导致申请失败。
-   内部碎片：伙伴系统强制按 $2^n$ 分配，可能浪费部分内存（如申请 3 页实际分配 4 页）。

回收机制的局限性

-   回收效率低：若回收的页多为活跃页（如内核数据结构），无法释放有效内存。
-   迁移类型隔离：不可移动页（如 DMA 缓冲区）会阻止伙伴合并，碎片长期存在。

系统级应对措施

-   调整水位线：通过 /proc/sys/vm/min_free_kbytes 提高最低水位，提前触发回收。
-   使用大页（THP）：减少小页分配需求，间接缓解碎片。
-   手动触发规整：通过 echo 1 > /proc/sys/vm/compact_memory 强制整理内存。

## 问题二：回收之后还不够会怎么办？

当申请内存时，如果当前没有足够大小的块，伙伴系统通过分裂上级块来满足需求；但如果连上级块也都用完了（即回收之前就已经全部分配），那么即使后续有内存被释放，可能仍然无法满足下一次的分配需求。

或者更具体地说：如果释放了一些内存块，但仍然没有足够大的连续块能满足新的分配请求，那会怎么样？

### 情况 1：释放了某个块，但还未合并成更大的块

-  当某个 2^k 的块被释放时，伙伴系统会**检查它的伙伴块是否也是空闲的**。
-  如果伙伴块**未空闲**，则**无法合并**，只能将当前块单独放回空闲链表。
-  ➤ **此时仍然没有更大的连续块产生，因此下次申请更大的内存仍可能失败。**

### 情况 2：释放后，伙伴也空闲，成功合并为更大的块

-  如果被释放的块和它的伙伴块都空闲，则它们会**合并为一个更大的 2^(k+1) 块**。
-  然后系统会**继续检查这个新合并的 2^(k+1) 块的伙伴是否也空闲**，如果是，就继续合并为 2^(k+2)，依此类推。
-  ➤ 这样可以**逐步形成更大的连续空闲块**，有利于后续更大的内存申请。

### 情况 3：即使回收了部分内存，仍然没有足够大的块满足申请

即使你释放了一些内存，可能出现如下情况导致分配仍然失败：

1. **释放的块没有与伙伴合并**（因为伙伴被占用），所以无法形成更大的块；
2. **释放的块虽然合并了，但仍然小于申请的大小**；
3. **所有更大块的伙伴也都被占用，无法进一步合并**；
4. **内存碎片化严重**：虽然总空闲内存足够，但没有**连续的、足够大的块**能满足分配需求（尤其是非伙伴系统或高级分配器更易遇到，但伙伴系统也可能存在类似问题，尤其在频繁分裂后）。

**结论**：即使释放了一些内存，如果这些释放的内存无法合并为足够大的、符合申请大小的连续块，那么下一次的内存申请仍然可能失败。

## 优势与局限

**优点**

-   减少外部碎片：通过合并机制回收连续空闲内存。
-   高效操作：拆分与合并仅需位运算，时间复杂度接近 $O(1)$。
-   简单结构：仅需维护固定阶的空闲链表。

**缺点**
-   内部碎片：强制按2的幂次分配可能导致浪费（如申请257KB需分配512KB）。
-   小对象不适用：需依赖SLAB分配器进一步细分。

## 实际应用

-   场景：主要用于分配大块连续内存（如DMA缓冲区、HugePages）。
-   协同机制：与SLAB分配器分工，前者管理页框，SLAB处理小对象（如内核结构体）。

## 扩展思考

1.   为什么会有“回收了但依然不够”的情况？

-  主要原因就是**内存碎片化**，尤其是**外部碎片**：虽然空闲内存总量够，但没有足够大的**连续物理/逻辑块**。
-  伙伴系统**减少外部碎片的能力强**，但对**频繁分裂后未能合并**的情况，仍可能出现“有空间但用不上”的问题。

2. 如何提高分配成功率？

-  **及时释放不再使用的内存**，尤其是大块内存；
-  **尽量减少内存申请的碎片化**（比如避免频繁申请释放不同大小的内存）；
-  在支持的情况下，使用**slab 分配器（针对小对象）、内存池等技术**优化特定场景的内存使用。

## 总结

| 问题                               | 情况描述                                                 | 处理方式 / 结果                                |
| ---------------------------------- | -------------------------------------------------------- | ---------------------------------------------- |
| **申请内存时发现没有足够大小的块** | 想申请 $2^k$，但空闲链表中没有，且上级块也都已分配       | 伙伴系统会尝试分裂更大的块，直到成功或失败     |
| **分裂到最大块仍无法满足**         | 所有更大的块（如 $2^{(k+1)}$、$2^{(k+2)}$...）都已被分配 | ✅ 内存申请失败（返回 NULL / -ENOMEM 等）       |
| **回收（释放）了内存块**           | 释放了一个块，但它的伙伴被占用，无法合并                 | ❌ 无法形成更大的块，可能仍无法满足后续大块申请 |
| **回收后伙伴也空闲，成功合并**     | 释放的块与伙伴都空闲，合并为更大的块，可能继续向上合并   | ✅ 可能产生更大的连续空闲块，有利于后续分配     |
| **回收后仍无法满足新的分配请求**   | 即使有释放，但没有足够大 / 连续的块                      | ❌ 申请仍可能失败，哪怕总空闲内存足够           |
