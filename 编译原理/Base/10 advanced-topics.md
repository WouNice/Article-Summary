# 第10章：高级专题——工业级编译器的实战智慧

**用一句话说清楚**：前 9 章教了"原理"，这一章教"实战"——当一个编译器走进真实世界，会遇到哪些教科书上没写的问题，以及工业界是怎么解决的。

## 词法分析方案纵深对比

| 方案 | 性能 | 场景 | 优势 | 不足 |
|------|------|------|------|------|
| **手写 Lexer** | ⚡ ⚡ ⚡ ⚡ ⚡ | 生产级编译器 | 完全可控、性能最优（比 Flex 快 30-50%） | 开发量大 |
| **Flex** | ⚡ ⚡ ⚡ ⚡ | 原型/小项目 | 开发快 | 性能一般 |
| **Ragel** | ⚡ ⚡ ⚡ ⚡ | 复杂词法 | 支持 DFA 和扫描动作 | 学习曲线陡 |

> 💡 **Clang、GCC、Rust、Go 全用手写词法分析器**——原因不仅是性能，更是因为手写能提供更好的错误信息和更灵活的处理。

## 最大匹配的两种策略

```c
// 策略1：长度+位置标记（推荐，低开销）
// 每次匹配时记录当前位置是哪个 Token 的终点
void record_longest_match(Token *tokens, int len) {
    int best_pos = -1;
    TokenKind best_tok = TOK_ERROR;

    // 每个 Token 匹配后，如果匹配长度更长就更新
    for (int i = 0; i < num_tokens; i++) {
        int match_len = try_match(tokens[i], input, pos);
        if (match_len > best_len) {
            best_len = match_len;
            best_tok = tokens[i];
            best_pos = pos + match_len;
        }
    }
    // 使用最长匹配的 Token
    return best_tok;
}
```

**最大匹配的核心**：当 `ifx` 输入时，词法分析器会尝试匹配所有模式——"if"匹配到 2 字符，但 `ifx` 作为标识符匹配到 3 字符。**总是选择最长的那个**。

## 语法分析方案的对比和选择

| 方案 | 代码量 | 表达能力 | 错误诊断 | 代表 |
|------|-------|---------|---------|------|
| **递归下降（手写）** | 约 60% 代码量减少 | 有限 | 极好（可定制消息） | Clang、GCC⚡、Rust、Zig |
| **LALR(1) 生成器** | 约 1000 行 yacc | 无限（LR 文法） | 一般 | Yacc/Bison 工具链 |
| **Pratt 解析** | 极简 | 表达式部分极优 | 好 | 几乎所有语言的表达式部分 |

> 💡 **一个反差事实**：GCC 早年间使用 Yacc/Bison 生成 LALR 解析器，后来改成了手写的递归下降——不是因为性能，而是因为**递归下降能给出更好的错误信息**。当你写 `int f( { }` 时，递归下降可以精确地说"第 3 行缺少参数"，而 LR 解析器只能说"第 3 行无法解析"。

## 错误恢复：让编译器"死而不僵"

一个好的编译器不会遇到第一个错误就停止——它应该**恢复**并继续检查后面的错误：

| 恢复策略 | 原理 | 典型恢复率 | 代表 |
|---------|------|-----------|------|
| **Panic Mode** （恐慌模式） | 跳过输入到同步点（如 `;`、`}`） | 70-80% | 最常用 |
| **短语级恢复** | 插入/删除/替换单个 Token | 80-90% | Clang |
| **全局恢复** | 计算最小编辑距离 | ~95% | 学术工具，太慢 |

**Panic Mode 实现示例：**

```c
void panic_recover(Lexer *lex, Token *sync_tokens, int count) {
    fprintf(stderr, "语法错误: 第 %d 行\n", lex->line);

    // 跳过输入直到遇到"安全"的同步 Token
    while (lex->cur_tok.kind != TOK_EOF) {
        for (int i = 0; i < count; i++) {
            if (lex->cur_tok.kind == sync_tokens[i]) {
                return;  // 找到同步点了，恢复！
            }
        }
        lex_advance(lex);  // 跳过当前 Token
    }
}
```

## 中间表示的深度选择

不同的 IR 适合不同的优化目标：

| IR 类型 | 适合场景 | 优化能力 | 代表 |
|--------|---------|---------|------|
| **TAC/SSA** | 标量优化（死代码消除、常量传播） | ★★★★★ | LLVM、GCC |
| **CPS/ANF** | 函数式语言优化 | ★★★★ | Haskell GHC |
| **AST** | 语法级分析、重构 | ★★ | 编译器前端自身 |
| **Sea-of-Nodes** | 激进全局优化 | ★★★★★ | V8 TurboFan |

## 优化级别的真实经验

| 级别 | 真实效果 |
|------|---------|
| **-O0** | 完全不优化，编译最快，常用于开发调试 |
| **-O1** | 做"安全的优化"——不会显著增加编译时间 |
| **-O2** | 大多数项目的推荐级别，平衡速度和代码质量 |
| **-O3** | ⚠️ 可能比 -O2 慢！大量内联导致 i-cache 压力 |
| **-Ofast** | 允许违反浮点标准的优化，高性能计算常用 |

```text
一个反例：某些数据库使用 -O3 后反而变慢了。
原因：函数内联过多 → 二进制膨胀 → CPU 指令缓存频繁失效 → 频繁去内存取指令
        VS
-O2 保持函数边界 → 指令缓存命中率高 → 整体更快

结论：-O3 on paper, -O2 in practice。逐个应用评测，不要盲信选择。
```

## 编译器的"速度 vs 质量"权衡

| 场景 | 推荐的编译器 | 原因 |
|------|------------|------|
| 快速迭代（开发中） | TCC / Cranelift | 增量编译减少 70% 时间 |
| 最终发布 | GCC -O2 / Clang -O2 | 代码质量最优 |
| 「只做一次」小程序 | TCC | 0.003 秒编译 100 行 |
| 大型项目发布版 | Clang | 编译比 GCC 快 50-100%，代码质量 103-105%（相比 GCC） |

> 💡 据统计，Clang 从 LLVM 12 开始（2022 年）生成的代码质量已经稳定超过 GCC，SPEC 基准测试达到 GCC 的 103-105%。但部分特定场景 GCC 仍有优势（嵌入式、浮点精度敏感计算）。

## 正则引擎选型的"安全指南"

| 场景 | 推荐引擎 | 原因 |
|------|---------|------|
| 编译器词法分析 | **DFA**（手写/Flex） | 线性时间，无 ReDoS |
| 用户输入搜索 | **DFA/Thompson NFA** | 防止输入导致服务崩溃 |
| 需要回溯 | **PCRE/RE2（带超时）** | 功能完整但有风险 |

## 📝 本章小结

| 知识点 | 一句话理解 |
|--------|-----------|
| **Panic Mode 恢复** | 遇到错误就跳到下一个 `;` 或 `}`，继续检查后面的错误 |
| **-O3 未必比 -O2 快** | 内联太多会导致指令缓存溢出 |
| **自举** | 编译器能编译自己——从"别人的代码"变成"自己的代码" |
| **ReDoS 攻击** | 恶意输入导致正则回溯爆炸，DFA 引擎天然免疫 |
