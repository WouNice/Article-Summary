# 缓存一致性方案

## 问题背景

在高并发系统中，Redis作为缓存层与MySQL持久化存储的组合被广泛采用。当系统需要同时更新Redis和MySQL时，由于网络延迟、服务故障或并发竞争等因素，可能产生以下典型问题：

1.  缓存穿透：写MySQL成功后Redis未更新，导致后续请求直接访问数据库
2.  脏数据覆盖：并发写操作导致Redis与MySQL更新顺序错乱
3.  状态不一致：部分成功（如MySQL成功但Redis失败）导致数据版本分裂

## 主流解决方案及对比

### 方案一：Cache Aside模式（旁路缓存）

实现步骤：

1.  写操作直接更新MySQL
2.  删除对应Redis缓存（非更新）
3.  读请求优先访问Redis，未命中时从MySQL加载

优点：

-   实现简单，避免并发写冲突
-   天然防缓存穿透（通过删除而非更新）
-   资源消耗可控（仅维护必要缓存）

缺点：

-   存在短暂不一致窗口期（删除缓存后到下次加载前）
-   需处理"先删缓存再写DB"与"先写DB再删缓存"的时序风险

### 方案二：双写事务控制

实现步骤：

1.  开启本地事务
2.  先更新MySQL，立即同步更新Redis
3.  通过事务保证原子性

优点：

-   理论强一致性
-   实时性最佳

缺点：

-   事务回滚复杂度高（需补偿机制）
-   网络抖动易导致事务失败
-   性能损耗显著（同步阻塞）

### 方案三：延迟双删策略

实现步骤：

1.  更新MySQL
2.  首次删除Redis
3.  延迟指定时间后再次删除Redis

优点：

-   缓解并发读写导致的脏数据
-   降低短暂不一致时间窗口

缺点：

-   延迟时间难以精确设定
-   无法完全消除不一致风险
-   需维护延迟任务队列

### 方案四：事务消息中间件

实现步骤：

1.  将写操作封装为事务消息
2.  MySQL提交后异步通知Redis
3.  通过消息队列保证最终一致性

优点：

-   解耦数据库操作
-   支持失败重试机制
-   系统扩展性强

缺点：

-   引入新组件增加架构复杂度
-   消息延迟导致短暂不一致
-   需处理消息积压问题

### 方案五：Binlog订阅同步

实现步骤：

1.  通过MySQL Binlog监听数据变更
2.  解析日志后同步到Redis
3.  使用Canal/Debezium等中间件

优点：

-   完全解耦业务代码
-   保证严格顺序性
-   支持全量/增量同步

缺点：

-   架构复杂度最高
-   同步延迟不可控
-   运维成本较高

### 其他

本人在实际项目中，见过一种：设置特殊值 + 休息一会，就是先跟新缓存中值为特殊值，然后进行修改数据库。读操作发现是特殊值，然后休息一会，再查。

## 方案选型建议

| 场景特征               | 推荐方案          | 一致性等级 | QPS支持  |
| :--------------------- | :---------------- | :--------- | :------- |
| 读多写少，容忍短暂延迟 | Cache Aside       | 最终一致   | 10万+    |
| 强一致性金融交易       | 双写事务+补偿机制 | 强一致     | 1万+     |
| 高并发写入场景         | 事务消息中间件    | 最终一致   | 5万+     |
| 历史数据分析系统       | Binlog订阅同步    | 最终一致   | 按需扩展 |

实际应用中，建议采用组合策略：核心业务使用Cache Aside+延迟双删，支付等关键链路采用事务消息，数据分析场景使用Binlog同步。同时需建立数据校对系统，定期对比Redis与MySQL数据差异，通过告警机制实现兜底保障。
