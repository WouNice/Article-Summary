# 第5章：基础设施即代码(IaC)

## 本章学习目标

- 理解基础设施即代码的核心价值与解决的核心痛点
- 掌握声明式与命令式的区别及适用场景
- 了解 Terraform / Pulumi / Ansible 等主流工具的定位
- 理解不可变基础设施的设计理念

## 为什么需要基础设施即代码

### 传统运维的痛点

想象一个场景：线上出现了一个奇怪的网络问题，排查了一整天后，有人问到："上个月谁 SSH 到这台机器改过 iptables？"

这就是**配置漂移（Configuration Drift）**的典型表现——服务器从初始状态逐渐偏离，最终变得"独一无二"（雪花服务器）。

### IaC 定义

> **基础设施即代码**是将服务器、网络、数据库、负载均衡器等基础设施的配置/管理，以声明式或命令式的代码形式进行版本控制、自动化管理的方法论。

### IaC 的核心价值

| 传统模式 | IaC 模式 |
|---------|---------|
| 手动创建服务器 | 代码定义，一键部署 |
| SSH 上去改配置 | 修改代码，重新应用 |
| "这台机器特殊" | 所有环境同源 |
| 环境不一致导致 Bug | "环境差异"消失 |
| 运维是瓶颈 | 开发者自助创建环境 |
| 回滚靠记忆 | 版本控制 + Git Revert |

## 声明式 vs 命令式

这是 IaC 中最核心的设计哲学差异。

### 命令式（Procedural / Imperative）

**关注"怎么做"**：你告诉系统每一步操作。

```bash
# 命令式示例：创建 ECS 实例
1. 创建一个安全组
2. 创建一个密钥对
3. 调用 RunInstances API
4. 检查实例状态
5. 分配弹性 IP
6. 等待实例初始化完成
```

```python
# Pulumi 的命令式编程风格
import pulumi_aws as aws

sg = aws.ec2.SecurityGroup("web-sg",
    description="Allow HTTP",
    ingress=[{"protocol": "tcp", "from_port": 80, "to_port": 80, "cidr_blocks": ["0.0.0.0/0"]}]
)

# 明确每一步怎么做
```

### 声明式（Declarative）

**关注"要什么"**：你描述最终状态，工具负责如何到达。

```hcl
# Terraform 声明式示例
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.medium"

  vpc_security_group_ids = [aws_security_group.web.id]
}

resource "aws_security_group" "web" {
  name        = "web-sg"
  description = "Allow HTTP"

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

### 对比

| 维度 | 命令式 | 声明式 |
|------|-------|--------|
| 思维模型 | "怎么做" | "要什么" |
| 幂等性 | 可能不幂等 | 天然幂等 |
| 状态管理 | 需自行维护 | 自动跟踪状态 |
| 学习曲线 | 更贴近编程思维 | 需要学习 DSL |
| 变更风险 | 操作顺序不当可能出错 | 自动消除漂移 |
| 代表工具 | Pulumi (SDK), CloudFormation | Terraform, AWS CDK |

> **业界趋势**：声明式已经成为 IaC 的主流范式，Terraform 是最广泛采用的标准。

## 主流 IaC 工具

### Terraform — 行业事实标准

| 特性 | 说明 |
|------|------|
| 创始人 | HashiCorp（2014） |
| 语言 | HCL（HashiCorp Configuration Language） |
| 模式 | 声明式 |
| 状态管理 | .tfstate 文件（本地或远程后端） |
| 提供商 | 2000+ Provider（AWS、Azure、GCP、K8s、VMware...） |

**核心工作流**：

```bash
terraform init      # 初始化模块和 Provider
terraform plan     # 预览变更
terraform apply    # 执行变更
terraform destroy  # 销毁资源
```

**状态文件管理**：
```
.terraform/
├── terraform.tfstate        # 当前状态
└── terraform.tfstate.backup # 备份
```

**最佳实践**：
- 永远不要手改 .tfstate！
- 使用远程存储（S3 + DynamoDB / Terraform Cloud）共享状态
- 用模块（Module）组织可复用的资源组
- 使用 Terraform Workspace 管理多环境

### Terraform 状态管理最佳实践

状态文件（.tfstate）是 Terraform 的核心资产，它记录了基础设施的当前状态，任何状态管理失误都可能导致生产事故。

#### 远程 State 存储方案对比

| 存储方案 | 后端类型 | 一致性 | 锁机制 | 月成本（100个资源） | 安全特性 | 适用场景 |
|---------|---------|--------|--------|-------------------|---------|---------|
| S3 + DynamoDB | s3 | 最终一致性（S3）<br>强一致性（DynamoDB 锁） | DynamoDB 表实现行级锁 | S3: ~$0.03/GB<br>DynamoDB: ~$0.50/月 | SSE-S3/AES-256<br>Bucket Policy + IAM | 中小团队，AWS 环境，<br>最广泛采用的方案 |
| Terraform Cloud/Enterprise | remote/cloud | 强一致性 | 内置分布式锁 | 免费版: 5 用户<br>Team: $20/人/月 | 原生加密<br>RBAC + 审计日志 | 企业团队，<br>需要协作工作流 |
| HashiCorp Consul | consul | 强一致性（Raft） | Session 锁 | 自建: 3 台服务器<br>托管: ~$35+/月 | ACL Token<br>TLS 加密 | 已有 Consul 基础设施<br>或需要服务发现的团队 |
| Azure Storage | azurerm | 强一致性 | Lease Blob 锁 | Blob: ~$0.05/GB<br>API 请求费 | Azure AD + RBAC<br>SSE | Azure 原生环境 |
| Google Cloud Storage | gcs | 强一致性 | Object 版本锁 | ~$0.026/GB | IAM + CMEK | GCP 原生环境 |
| PostgreSQL | pg | 强一致性 | 行级锁 | 自建/云托管 | 表级加密<br>迁移友好 | 已有 PG 集群，<br>希望统一存储 |

#### 状态锁定机制详解

```
S3 + DynamoDB 方案架构：

┌─────────────────────────────────────────────────┐
│                  Terraform CLI                     │
├─────────────────────────────────────────────────┤
│  1. terraform apply                                │
│     │                                              │
│     ├→ DynamoDB: 写入锁记录 (LockID=state_path)    │
│     │   - 成功: 继续执行                           │
│     │   - 失败(已锁): 阻塞等待或报错               │
│     │                                              │
│  2. 执行资源变更                                    │
│     │                                              │
│  3. 写入新 State 到 S3                              │
│     ├→ 写失败 → 回滚变更，DynamoDB 释放锁           │
│     │                                              │
│  4. DynamoDB: 删除锁记录                            │
└─────────────────────────────────────────────────┘
```

#### DynamoDB 锁表配置

```hcl
terraform {
  backend "s3" {
    bucket         = "my-company-terraform-state"
    key            = "prod/network/terraform.tfstate"
    region         = "ap-northeast-1"
    encrypt        = true
    dynamodb_table = "terraform-state-lock"
  }
}
```

DynamoDB 锁表创建（推荐配置）：

```bash
aws dynamodb create-table \
  --table-name terraform-state-lock \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST
```

#### 状态文件安全原则

1. **State 文件是机密数据**：它可能包含数据库密码、API 密钥、连接字符串等敏感信息
2. **永远不要提交到 Git**：.tfstate 应列入 .gitignore
3. **启用加密**：S3 后端必须设置 `encrypt = true`，使用 SSE-S3 或 KMS
4. **最小化敏感信息**：使用 Terraform 的 `sensitive = true` 标记输出；优先用 Vault/Secrets Manager 而非明文
5. **版本控制 State 文件**：S3 开启版本控制，可回溯历史状态
6. **访问控制**：对 State 存储配置严格的 IAM 策略，仅 CI/CD 管道和核心运维可读写

## 不可变基础设施

### 概念

> 服务器一旦创建，**绝不**就地修改。任何变更都通过**重建实例**来实现。

### 传统：可变基础设施

```
服务器上线 → 安装软件 → 修改配置 → 安全补丁 ... → 雪花服务器
             ↑________ 每次修改都可能导致漂移 ________↓
```

### 不可变模式

```
问题：更新应用版本
方案：不修改现有服务器，直接基于新版本构建新镜像 → 启动新实例 → 替换旧实例
回滚：直接切回旧镜像
```

### 实践落地

```
应用代码变更
    ↓
CI 构建新镜像（版本号 v2.0.0）
    ↓
用 Packer / Docker build 生成不可变镜像
    ↓
Terraform 声明：run 这个新镜像
    ↓
滚动/蓝绿替换旧实例
```

### 好处

| 好处 | 说明 |
|------|------|
| 消除配置漂移 | 每台服务器从同一个镜像启动 |
| 明确回滚 | 回滚 = 跑旧版本镜像 |
| 可审计 | 每个镜像对应一个 Build ID |
| 简化排错 | "机器"不再有特殊状态 |
| 安全基线 | 镜像构建时即包含安全配置 |

## 模块化设计原则

### 为什么需要模块化

在规模化 IaC 实践中，每个业务线都重复编写 VPC 定义、ECS 模版、RDS 配置，导致：
- 代码重复率超过 70%，维护成本高昂
- 配置参数不统一，生产环境的安全组规则比测试环境少一半
- 版本混乱，没人知道当前线上跑的 VPC 是哪版代码定义的

**模块化（Module）设计是解决这些问题的关键。**

### Terraform Module 设计规范

#### 模块结构标准

```
terraform-module-aws-vpc/
├── main.tf                 # 核心资源定义
├── variables.tf            # 输入变量声明
├── outputs.tf              # 输出值定义
├── README.md               # 使用文档（必须）
├── examples/               # 使用示例
│   └── basic/
│       ├── main.tf
│       └── terraform.tfvars
├── tests/                  # 测试（Terratest 或 tf test）
│   └── vpc_test.go
└── versions.tf             # Provider 版本约束
```

#### 模块设计黄金法则

| 原则 | 说明 | 反例 | 正确做法 |
|------|------|------|---------|
| **单一职责** | 一个模块只做一件事 | 一个模块创建 VPC + ECS + RDS | VPC 模块、ECS 模块、RDS 模块分开 |
| **接口明确** | 最小化输入变量，清晰定义输出 | 50 个变量，文档缺失 | 核心变量 5-10 个，文档化每个变量 |
| **版本化** | 使用语义化版本发布模块 | 直接引用 GitHub master 分支 | `source = "git::ssh://git@github.com/...?ref=v1.2.0"` |
| **可组合** | 模块可以像乐高一样组合 | 模块 A 依赖模块 B 的内部资源 | 通过 outputs 传递依赖 |
| **无状态** | 模块内不定义 backend | backend {} 写在模块里 | backend 在根模块统一配置 |
| **默认安全** | 默认配置遵循安全最佳实践 | 默认安全组放通 0.0.0.0/0 | 默认只放通最小必要端口 |

#### 变量设计规范

```hcl
# variables.tf 示例

# 必须提供的变量（无默认值）
variable "vpc_cidr" {
  description = "VPC 的 CIDR 块，如 10.0.0.0/16"
  type        = string

  validation {
    condition     = can(cidrhost(var.vpc_cidr, 0))
    error_message = "必须提供有效的 CIDR 表示法。"
  }
}

# 有安全默认值的变量
variable "enable_nat_gateway" {
  description = "是否创建 NAT Gateway（生产环境推荐 true）"
  type        = bool
  default     = true
}

# 复杂类型变量
variable "subnet_configs" {
  description = "子网配置列表"
  type = list(object({
    name              = string
    cidr              = string
    availability_zone = string
    public            = bool
  }))
  default = []
}
```

#### 模块版本管理策略

```
引用方式对比：

# ❌ 永远不要用 latest 或 master
source = "github.com/my-company/terraform-module-vpc"

# ❌ 不要用无版本号的 commit
source = "github.com/my-company/terraform-module-vpc//modules/public-subnet"

# ✅ 使用语义化版本（推荐）
source = "git::ssh://git@github.com/my-company/terraform-module-vpc.git?ref=v2.1.0"

# ✅ 私有模块注册表（企业）

```

```
  特征：共享的 modules/ 目录，多环境引用

  特征：独立 Git 仓库，语义化版本标签

  特征：Terratest 测试，CI 自动发布，文档自动生成
  状态：推荐状态——模块就是产品
```

## IaC 安全合规

### 为什么 IaC 需要安全合规

当基础设施变成代码，安全问题的面也扩大了：
- 开发者通过 IaC 可以直接创建安全组、IAM Role、S3 存储桶
- 错误配置（如 S3 公开可读、安全组 0.0.0.0/0）会被自动化地批量部署
- State 文件本身可能泄露数据库密码等敏感信息

### Policy as Code（策略即代码）

> **Policy as Code** 是将安全合规规则编写为可执行代码，在 IaC 生命周期中自动检查的策略引擎。

#### 主流策略引擎对比

| 特性 | OPA (Open Policy Agent) | HashiCorp Sentinel | AWS Config Rules | Kyverno |
|------|------------------------|-------------------|-----------------|---------|
| 策略语言 | Rego | Sentinel DSL | JSON/YAML + Lambda | YAML |
| 开源/商业 | 开源（CNCF 毕业项目） | 商业（Terraform Cloud Enterprise） | 商业（AWS 原生） | 开源（CNCF） |
| 适用平台 | 任意（Terraform/K8s/Envoy/...） | Terraform 生态 | AWS 资源 | Kubernetes |
| 策略生效时机 | CI 管道检查 / 准入控制 | Terraform Plan 阶段 | 事后检测 | K8s 准入控制 |
| 测试能力 | 内置 Rego 测试框架 | 内置 | 手动测试 | 有限 |
| 学习曲线 | 中（需学 Rego） | 低（类 HCL） | 低 | 低 |

#### OPA + Terraform 实践

OPA 可以在 Terraform Plan 阶段拦截不合规的变更。

策略示例——禁止 S3 桶公共读取：

```rego
# policy/s3_public_access.rego
package terraform.s3

deny[msg] {
  resource := input.resource.aws_s3_bucket[_]
  resource.config.acl == "public-read"
  msg := sprintf("S3 桶 %s 不允许设为 public-read，请使用 private 或 bucket-owner-full-control", [resource.config.bucket])
}

deny[msg] {
  resource := input.resource.aws_s3_bucket[_]
  resource.config.acl == "public-read-write"
  msg := sprintf("S3 桶 %s 不允许设为 public-read-write", [resource.config.bucket])
}
```

CI 管道集成 OPA 检查：

```bash
# CI 脚本片段（GitHub Actions / GitLab CI）
# 生成 Terraform Plan
terraform plan -out=tfplan.binary
terraform show -json tfplan.binary > tfplan.json

# OPA 策略检查
opa eval --format pretty \
  --data policy/ \
  --input tfplan.json \
  "data.terraform.s3.deny"

# 如果有拒绝，阻止 apply
if [ $? -ne 0 ]; then
  echo "❌ 安全策略违规，请修复后重新提交"
  exit 1
fi
```

#### Sentinel（Terraform Cloud 内置）

Sentinel 是 Terraform Cloud Enterprise 的内置策略引擎，策略以类似 HCL 的语法编写：

```sentinel
# 强制要求资源具有 Environment 标签
import "tfplan/v2" as tfplan

allResources = filter tfplan.resource_changes as _, rc {
  rc.mode == "managed"
}

# 检查所有资源是否有 Environment 标签
validate = rule {
  all rc in allResources {
    rc.change.after.tags else {} contains "Environment"
  }
}

main = rule {
  validate else "所有资源必须包含 Environment 标签"
}
```

### 常见 IaC 安全反模式及修复

| 反模式 | 风险等级 | 示例 | 修复方案 |
|--------|---------|------|---------|
| S3 桶公开读取 | 严重 | `acl = "public-read"` | 改成 `acl = "private"`，通过 CloudFront + OAI 对外提供服务 |
| 安全组 0.0.0.0/0 | 严重 | `cidr_blocks = ["0.0.0.0/0"]` | 指定具体来源 IP 或使用 Security Group ID 引用 |
| 硬编码密钥 | 严重 | `password = "admin123"` | 使用 `aws_secretsmanager_secret` 或 `vault_generic_secret` |
| IAM 权限过宽 | 高 | `Action = ["*"]` 或 `Resource = ["*"]` | 最小权限原则，精确到具体 Action 和 Resource ARN |
| 未加密的 EBS/RDS | 高 | `encrypted = false`（默认） | 设置 `encrypted = true`，指定 KMS Key |
| State 文件明文存 Git | 严重 | `.tfstate` 提交到仓库 | 设置远程后端 + .gitignore |
| 缺少资源标签 | 中 | 无 tags 定义 | 使用 `default_tags` 统一配置，强制标签策略 |
| 使用 latest 镜像 | 高 | `ami = "data.aws_ami.ubuntu.id"` + 无版本固定 | 固定 AMI ID 或使用 SSM Parameter 管理 |

```hcl
  }
```


### 安全原则

1. **永不硬编码密钥**：使用 Secrets Manager / Vault
2. **最小权限**：Terraform 使用的 IAM Role/User 只给所需的最小权限
3. **远程状态加密**：S3 后端启用 SSE，DynamoDB 用于状态锁
4. **评审 IaC 变更**：如同评审代码一样，IaC 变更也需要 Code Review
5. **状态文件是敏感数据**：可能包含 Secret，切勿提交到 Git

### 常见反模式

| 反模式 | 问题 | 改进 |
|--------|------|------|
| 手动修改云控制台 | 配置漂移 | 所有变更走 IaC |
| 一个巨型 tf 文件 | 难以维护 | 模块化拆分 |
| .tfstate 提交到 Git | 安全风险 + 冲突 | 远程后端 |
| Apply 前不看 Plan | 意外变更 | 团队内要求 Plan 评审 |
| 跳过 Terraform 直接 SSH | 漂移 | 用不可变基础设施 |

## 生产案例：某金融科技公司的基础设施大迁移

### 业务背景

**公司概况**：
- 某中型金融科技公司（持牌经营，员工 800+ 人）
- 核心业务：线上信贷审批系统、智能风控平台、资金清结算系统
- 基础设施规模：500+ 台 ECS 实例，分布在 3 个环境（Dev/Staging/Prod）

**迁移前状况**：
```
时间线：公司从初创 20 人发展到 800 人
基础设施演进：
  Year 1-2:  5 台服务器 → Web 控制台手动创建
  Year 3:    50 台服务器 → 几个 Shell 脚本 + Screenshot 记配置
  Year 4-5:  200 台服务器 → 配置开始"个性化"
  Year 6:    500+ 台服务器 → 彻底失控
```

**核心痛点**：

| 问题 | 严重程度 | 具体表现 |
|------|---------|---------|
| 配置漂移率 > 80% | 🔴 严重 | 生产环境 200 台 ECS 中 170 台的 /etc/hosts、Nginx 配置、iptables 规则各不相同 |
| 环境不一致 | 🔴 严重 | 开发环境用 CentOS 7.6，测试环境用 Alibaba Cloud Linux 2，生产环境用 CentOS 7.9 |
| 无法通过审计 | 🔴 致命 | 金融监管机构要求：所有服务器配置必须有版本历史、变更记录、定期审计报告。现状：一张 Excel + SSH 记录 |
| 环境交付时间 | 🟡 中 | 一个新环境从提出到交付平均 2 天（需要运维逐台创建、配置、验证） |
| 故障恢复 | 🔴 严重 | 服务器宕机后无法快速重建，最慢一次 ECS 故障导致业务中断 6 小时 |
| 新人上手 | 🟡 中 | 新运维入职需要 2-3 个月才能"熟悉"各环境的"特殊配置" |

```yaml
        src: templates/app.service.j2
        dest: "/etc/systemd/system/{{ app_name }}.service"

        name: "{{ item.key }}"
        value: "{{ item.value }}"
        state: present

        - { key: net.core.somaxconn, value: "1024" }
        - { key: vm.swappiness, value: "10" }
```

### 经验教训

1. **人比工具更重要**
   - 推行 IaC 的最大阻力不是技术，而是让运维团队从"手动操作"范式转向"代码思维"范式
   - 安排 2 周的培训+结对编程过渡期，让团队逐步适应

2. **分阶段迁移，切忌大爆炸**
   - 某模块试图一次迁移整个核心业务系统，发生故障后花了 3 小时回退
   - 教训：每次迁移只换一个子模块，保留回退能力

3. **State 文件就是你的"命根子"**
   - 迁移过程中曾因 S3 后端配置错误导致 State 文件损坏，最终不得不从备份恢复
   - 教训：S3 开启版本控制 + 定时备份 State 文件 + DynamoDB 锁必须启用

4. **All-or-Nothing 策略不可取**
   - 初期试图对所有 500+ 台 ECS 一次性迁移，发现排期完全不可行
   - 教训：先做小范围 PoC（QA 环境 20 台），验证流程无误后再推广

5. **安全合规并非事后补充**
   - OPA Policy 在 Plan 阶段拦截不合规配置，减少了 90% 的人为失误
   - 安全左移：在 CI 阶段自动扫描 IaC 安全风险（tfsec/Checkov）

6. **文档即代码**
   - 将所有环境信息（IP 段、域名、配置参数）更新到 Terraform 代码注释中
   - 每次 Apply 自动生成基础设施拓扑图的 JSON 描述，供架构师审查

## 本章小结

| 要点 | 说明 |
|------|------|
| IaC 核心 | 用代码定义和管理基础设施，消除手动操作和配置漂移 |
| 声明式 vs 命令式 | 声明式（"要什么"）是主流，天然幂等 |
| 工具定位 | Terraform/Pulumi 负责创建编排，Ansible 负责配置管理 |
| 状态管理 | 远程 State（S3 + DynamoDB）是生产推荐方案，锁机制避免并发冲突 |
| 模块化设计 | 单一职责、版本控制、接口明确、默认安全 |
| 安全合规 | Policy as Code + State 加密 + 安全扫描 = 合规护城河 |
| 不可变基础设施 | 不修改已有实例，通过重建实现变更 |
| 实践要点 | 模块化、远程状态、Code Review、最小权限 |
| 关键文件 | .tfstate 是敏感数据，须远程存储 + 加密 |
