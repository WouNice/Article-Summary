## 可观测性：不只是"监控"

### 概念分层

```
监控（Monitoring）    → 我知道系统出问题了
可观测性（Observability） → 我知道系统为什么出问题了
```

> 可观测性（Observability）源自控制理论，指系统内部状态可以从其外部输出推断的程度。在软件工程中，我们通过三类数据来达到可观测性。

### 可观测性三大支柱

```
┌────────────────────────────────────────────┐
│             可观测性                        │
│                                            │
│  ┌────────┐  ┌────────┐  ┌────────┐       │
│  │ 指标   │  │ 日志   │  │ 链路   │       │
│  │Metrics │  │ Logs   │  │Traces │       │
│  └────────┘  └────────┘  └────────┘       │
│  聚合后     │  离散     │  请求级          │
│  数值统计    │  事件记录   │  调用路径        │
└────────────────────────────────────────────┘
```

| 支柱 | 典型问题 | 数据特征 | 存储 |
|------|---------|---------|------|
| **指标** | 错误率上升了？ | 聚合数值、时间序列 | Prometheus / InfluxDB |
| **日志** | 什么错误消息？ | 文本事件、结构化 JSON | Elasticsearch / Loki |
| **链路** | 请求在哪一步慢了？ | Span 树、调用关系 | Jaeger / Tempo |

### 三者关联

```mermaid
# 请求通过三层数据关联
日志行包含 trace_id → 通过 trace_id 查链路
链路 span 包含 duration → 聚合为指标
指标告警触发 → 查对应时间窗口的日志和链路
```

## 指标监控：Prometheus + Grafana

### Prometheus 核心概念

**Pull 模型**：Prometheus Server 定期拉取（scrape）目标（target）暴露的指标端点。

```
                  ┌──────────────┐
                  │  Prometheus  │
                  │   Server     │
                  └──────┬───────┘
                    scrape│    ↑
          ┌───────────────┼────┴──────────┐
          │               │               │
          ▼               ▼               ▼
   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ Service A│   │ Service B│   │  Node    │
   │ :/metrics│   │ :/metrics│   │Exporter  │
   └──────────┘   └──────────┘   └──────────┘
```

**指标类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **Counter** | 只增不减的计数器 | 请求总数、错误总数 |
| **Gauge** | 可增可减的度量 | 当前连接数、内存使用 |
| **Histogram** | 分布的直方图 | 请求延迟分布 |
| **Summary** | 预计算的分位数 | P50/P90/P99 延迟 |

```promql
# PromQL 查询示例
rate(http_requests_total[5m])                        # 5分钟内的请求速率
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))  # P99 延迟
avg(container_memory_usage_bytes{namespace="prod"})   # 平均内存使用
```

### Grafana：可视化平台

```
                     ┌──────────┐
   Prometheus ──────→│          │
   Loki       ──────→│  Grafana │
   Tempo      ──────→│          │
   CloudWatch ──────→│          │
                     └──────────┘
```

**Grafana 最佳实践**：
- 按服务/功能分 Dashboard
- 每个 Dashboard 包含：
  - **4 个黄金信号**：延迟、流量、错误、饱和度
  - 业务指标看板
  - 资源利用率看板
- 使用 Annotation 标记发布事件

### 指标存储方案对比：大规模场景下的选型指南

当单机 Prometheus 无法满足规模需求时（通常 metrics 基数超过 1000 万或服务器超过 50 台），需要引入分布式指标存储方案。以下是主流方案的对比。

**选型决策树（三步法）**：

```
第一步：规模评估
  ├── 单机 < 100万 series / < 50台主机 → 原生 Prometheus 足够
  └── 需要长期存储 (>30天) 或 规模更大
      ├── 需要 Prometheus API 兼容 → 继续
      └── 可接受新协议 → 考虑 InfluxDB/ClickHouse

第二步：功能需求
  ├── 全局查询 + 长期存储 → Thanos 或 VictoriaMetrics
  ├── 多租户 + 高写入吞吐 → Cortex 或 Mimir
  └── 极致存储压缩 / 边缘资源受限 → VictoriaMetrics

第三步：运维能力
  ├── K8s 原生运维好 → Thanos / Cortex / Mimir
  ├── 单二进制易部署 → VictoriaMetrics
  └── 已有 Cassandra/S3 基础设施 → M3DB
```

**方案对比矩阵**：

| 维度 | Prometheus TSDB | Thanos | VictoriaMetrics | Cortex | M3DB |
|------|----------------|--------|-----------------|--------|------|
| **定位** | 单机 TSDB | Prometheus 长期存储扩展 | 高性能 TSDB 替代 | 云原生多租户 TSDB | 大规模分布式 TSDB |
| **存储效率** | 基准 (1x) | 约 0.7x (压缩比好) | 约 0.3x-0.5x (极佳) | 约 0.8x | 约 0.5x |
| **查询性能** | 最优 (本地读) | 中 (需合并多个 Store) | 高 (自行实现 vmstorage) | 中 (Querier 合并) | 中 (依赖 Cassandra) |
| **高可用** | 无原生 (需双写或备用) | 内置 Store Gateway HA | 内置 vminsert/vmselect HA | 多副本原生 HA | 多副本原生 HA |
| **长期存储** | 依赖本地盘，扩容麻烦 | S3/GCS 对象存储 | S3/GCS 对象存储 | S3/GCS | 自身集群 |
| **全局视图** | 不支持 | Sidecar + Querier | vmselect 原生支持 | Querier | Coordinator |
| **多租户** | 不原生支持 | 不支持 | 企业版支持 | 原生 | 原生 |
| **推/拉** | Pull 为主 | Pull (继承 Prometheus) | 支持 Push + Pull | Push 为主 | Push |
| **单二进制** | 是 | 否 (多组件) | 是 (单文件) | 否 (多组件) | 否 |
| **运维复杂度** | 低 | 中-高 (多组件协调) | 低-中 | 高 (依赖微服务) | 高 (强依赖 Cassandra) |
| **社区活跃度** | CNCF 毕业 | CNCF 毕业 | 独立 (极活跃) | CNCF 孵化 | Uber 开源 (社区一般) |
| **典型部署规模** | < 50 台节点 | 100-1000 台 | 100-5000 台 | 100-1000 台 | 500+ 台 |

**场景-方案匹配**：

| 典型场景 | 推荐方案 | 理由 |
|---------|---------|------|
| 已有成熟的 Prometheus 部署，需要长期存储 | **Thanos** | 最小改动，Sidecar 模式增量接入 |
| 新项目搭建监控体系，需要高性能 + 低存储成本 | **VictoriaMetrics** | 单二进制部署，存储压缩比极高，查询快 |
| 云原生 SaaS 平台，多租户隔离需求 | **Grafana Mimir** | 多租户原生支持，兼容 PromQL，Grafana 生态整合 |
| 超大规模 (千万级 series)，已有 Cassandra 基础设施 | **M3DB** | Uber 生产验证，单集群管理百万级指标源 |
| 小团队，K8s 小规模 (10-50 节点) | **原生 Prometheus 就够了** | 零额外运维成本，后续可平滑升级 Thanos |

**VictoriaMetrics 突出的存储优势**（实测数据）：
- 相比 Prometheus TSDB，存储空间减少 50%-70%
- 数据摄取性能是 Prometheus 的 10 倍以上（单节点 B 级 samples/s 吞吐）
- 支持 PromQL 兼容 + MetricsQL 扩展（如 `rollup_rate` 等便捷函数）
- 架构简单：`vminsert` + `vmstorage` + `vmselect` 三个组件，也可单二进制运行

**何时不应该选这些方案**：

```
小规模 (< 20 台服务器)
├── 直接使用 Prometheus 原生 + 本地 SSD
└── 引入 Thanos/VictoriaMetrics 徒增运维成本

团队无人熟悉分布式存储
├── 优先 Thanos（社区丰富、文档完善）
└── 避免 M3DB（运维极其复杂）

仅有简短保留期 (< 15 天)
├── Prometheus 原生足够
└── 长期存储方案多余的
```

## 日志管理：ELK vs Loki

### ELK Stack

```bash
Filebeat → Logstash → Elasticsearch → Kibana
  采集        处理        存储/索引      可视化
```

**特点**：
- 全文搜索能力强
- 索引成本高，存储量大时成本上升快

### Loki（Grafana 生态）

```
Promtail → Loki → Grafana
  采集      存储      查询
```

**特点**：
- 不做全文索引，只索引标签 → 成本低
- 与 Prometheus 使用相同的标签体系
- 查询效率略低于 ES

### 结构化日志规范

```json
// 好的日志格式（结构化 JSON）
{
  "timestamp": "2026-06-09T07:30:00Z",
  "level": "ERROR",
  "service": "user-service",
  "trace_id": "abc123def456",
  "user_id": "u-1001",
  "message": "Failed to authenticate user",
  "error": {
    "type": "AUTH_FAILED",
    "detail": "Invalid token: token expired"
  }
}
```

**日志级别规范**：

| 级别 | 使用时机 | 举例 |
|------|---------|------|
| **FATAL** | 系统无法继续运行 | 数据库连接完全丢失 |
| **ERROR** | 需要立即关注的问题 | 请求失败、支付异常 |
| **WARN** | 值得关注但不紧急 | 重试、限流接近阈值 |
| **INFO** | 重要业务事件 | 用户注册、订单创建 |
| **DEBUG** | 开发调试信息 | 变量值、请求详情（默认关闭） |

### 日志存储与查询的成本优化

日志通常是可观测性体系中最大的成本来源。一个日处理 10TB 日志的典型 ELK 集群，存储费用可能占到总成本的 70% 以上。以下是三个核心优化维度。

**维度一：日志采样策略对比**

| 策略 | 原理 | 优势 | 劣势 | 适用场景 |
|------|------|------|------|---------|
| **头采样（Head Sampling）** | 在日志产生时按概率决定是否保留（如 10% 采样率） | 实现简单，CPU 开销低 | 丢失低概率事件的上下文，无法保证追踪完整性 | 调试日志、低重要性 INFO 日志 |
| **尾采样（Tail Sampling）** | 先将所有日志写入缓冲区，根据规则（如错误 Trace）决定保留哪些 | 保留高价值事件（错误 Trace 100% 保留），采样更智能 | 需要缓冲队列，增加内存和延迟开销 | 分布式追踪日志，需保留错误全链路上下文 |
| **一致性采样（Consistent Sampling）** | 基于 Trace ID 的 Hash 值决定采样，同一 Trace 的所有 span 要么全保留要么全丢弃 | 保证 Trace 完整性，可还原完整调用链 | 实现稍复杂，需要 Trace ID 生成策略配合 | OpenTelemetry 全链路追踪场景 |

**实施建议**：
- 默认对所有 DEBUG 级别日志使用头采样（采样率 ≤ 1%）
- 对 ERROR/FATAL 级别日志**不采样**（全部保留）
- 对 WARN 级别日志使用 10%-50% 头采样
- 分布式追踪场景启用尾采样，保证错误 Trace 100% 保留，成功 Trace 低比例保留

**维度二：日志保留周期分层（保留策略）**

```
┌─────────────────────────────────────────────────┐
│                  日志数据湖                        │
├────────────┬────────────┬────────────────────────┤
│    热层    │    温层    │          冷层          │
│  (7天)     │ (8-30天)   │        (31-365天)      │
├────────────┼────────────┼────────────────────────┤
│ SSD/NVMe   │ HDD/SATA   │ S3/OSS/Blob Storage    │
│ 高吞吐写入  │ 批量查询    │ 低频访问/审计需求      │
│ 实时分析    │ 日常巡检    │ 合规保留              │
│ 成本: 3x   │ 成本: 1x   │ 成本: 0.1x-0.2x       │
└────────────┴────────────┴────────────────────────┘
```

**分层配置示例（Loki）**：

```yaml
# loki.yaml 保留周期配置
storage_config:
  boltdb_shipper:
    active_index_directory: /data/loki/index   # SSD 路径
    cache_location: /data/loki/cache           # SSD 路径
    shared_store: s3

# 热数据: 本地 SSD，7 天
# 温数据: 本地 HDD + S3 缓存，8-30 天
# 冷数据: S3 对象存储，31-365 天
table_manager:
  retention_deletes_enabled: true
  retention_period: 365d  # 总保留 1 年

  # 分区策略
  schema_config:
    configs:
      - from: 2026-01-01
        store: boltdb-shipper
        object_store: s3
        schema: v12
        index:
          prefix: loki_index_
          period: 24h  # 每日一个分区
```

**维度三：结构化日志的 Schema 设计**

好的 Schema 设计直接影响查询性能和存储成本：

| 设计原则 | 说明 | 效果 |
|---------|------|------|
| **标签 vs 字段分离** | 频繁查询的字段设为 Label（如 service、env、level），其他设为结构化字段 | Label 索引快但基数有限，字段搜索慢但灵活 |
| **避免高基数 Label** | 不要将 user_id、request_id、IP 设为 Label（基数 > 10000 的字段会严重拖慢索引） | 防止 Label 索引膨胀爆炸 |
| **字段类型精简** | 数字字段统一为 float64，字符串字段适当限制长度（如 message 截断到 1024 字符） | 减少存储空间 20%-40% |
| **降维处理** | 将重复出现的错误摘要化为 error_code（int），减少冗余文本存储 | 查询更快，压缩比更高 |
| **只保留有用字段** | 移除 request_id、timestamp 等重复或系统自动附加的冗余字段 | 每行减少 30%-50% 体积 |

**日志 Schema 设计对比**：

```json
// ❌ 不良 Schema：高基数 Label + 冗余字段
// 标签: {service, user_id, request_id, ip, env}
// 存储开销大，user_id 作为标签导致索引爆炸
{
  "user_id": "u-1001",       // 高基数 → 不应是 Label
  "request_id": "req-xxx",   // 高基数 → 不应是 Label
  "ip": "10.0.0.1",          // 高基数 → 不应是 Label
  "timestamp": "...",        // Loki 自动添加
  "message": "..."
}

// ✅ 良好 Schema：低基数标签 + 精简字段
// 标签: {service, env, level}
// 字段内包含高基数信息，不创建倒排索引
{
  "service": "order-svc",    // 低基数 → 作为 Label ✓
  "env": "prod",             // 低基数 → 作为 Label ✓
  "level": "ERROR",          // 低基数 → 作为 Label ✓
  "error_code": 4013,        // 降维后的错误码
  "message": "Auth failed"   // 截断到 256 字符
  // user_id、request_id 仅在需要时作为日志内容字段
}
```

## 分布式追踪

### 为什么需要链路追踪

一个请求在微服务架构中的旅程：

```
客户端 → API Gateway → Auth Service → Order Service → Payment Service → Database
                                                                 → Notification
```

如果响应变慢，是哪个环节的问题？**链路追踪提供了请求级的端到端视图。**

### OpenTelemetry

OpenTelemetry 是 CNCF 的**可观测性标准**，统一了指标、日志、链路的**数据采集接口**。

```
                        ┌─────────────────┐
                        │ OpenTelemetry    │
                        │ Collector        │
                        └────────┬────────┘
                 ┌───────────────┼────────────────┐
                 │               │                │
                 ▼               ▼                ▼
           ┌─────────┐   ┌──────────┐   ┌──────────┐
           │Prometheus│   │ Jaeger   │   │   Loki   │
           │  (指标)  │   │  (链路)  │   │  (日志)  │
           └─────────┘   └──────────┘   └──────────┘
```

**核心概念**：

```
Trace（完整请求）
└── Span（一次调用）
    ├── SpanKind: INTERNAL / SERVER / CLIENT / PRODUCER / CONSUMER
    ├── Attributes: 标签信息（HTTP method, URL...）
    ├── Events: 事件日志（"cache miss", "retrying"）
    └── Status: OK / ERROR
```

**代码示例**：

```go
// Go 中使用 OpenTelemetry
tracer := otel.Tracer("order-service")
ctx, span := tracer.Start(ctx, "CreateOrder")
defer span.End()

// 记录属性
span.SetAttributes(
    attribute.String("order.id", orderID),
    attribute.Float64("order.amount", amount),
)

// 调用下游服务（传播 context）
paymentResp, err := paymentClient.Pay(ctx, req)
if err != nil {
    span.SetStatus(codes.Error, err.Error())
    span.RecordError(err)
    return err
}
```

## 告警体系

### 告警设计原则

```
告警是信号，不是噪音
```

| 原则 | 说明 |
|------|------|
| **可行动** | 收到告警后必须有人能做的动作 |
| **可避免** | 静态阈值要设合理，避免频繁触发 |
| **有优先级** | 区分 P0（立即响应）到 P3（工作时间处理）|
| **有上下文** | 告警消息要包含足够信息：影响面、当前值、阈值 |
| **去重** | 防止告警风暴，同一个根因不重复报警 |

### 典型告警规则

```yaml
# Prometheus Alertmanager 规则示例
groups:
  - name: service-availability
    rules:
      # 高错误率
      - alert: HighErrorRate
        expr: job:http_errors:rate5m{job="api"} > 0.05
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.job }} 错误率超过 5%"

      # 高延迟
      - alert: HighLatency
        expr: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) > 0.5
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "P99 延迟超过 500ms"

      # 实例宕机
      - alert: InstanceDown
        expr: up == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 宕机"
```

### 告警疲劳与降噪策略

在生产环境中，告警数量经常远超处理能力，导致"狼来了"效应——值班工程师开始忽略告警。以下是 Alertmanager 提供的核心降噪机制。

**告警聚合（Grouping）**：将相似告警合并为一条通知

```
原始告警流:                   聚合后：
Instance A down               [3 个实例] 在 [prod] 命名空间宕机
Instance B down      →        └── Instance A (10.0.0.1)
Instance C down                  Instance B (10.0.0.2)
                                Instance C (10.0.0.3)
```

```yaml
# Alertmanager 聚合配置
route:
  group_by: ['namespace', 'severity']  # 按命名空间和严重级别分组
  group_wait: 30s                      # 收到第一个告警后，等待 30s 再发送（收集更多同类告警）
  group_interval: 5m                   # 同一组告警的重复通知间隔
  repeat_interval: 4h                  # 如果告警未解决，每 4 小时重复通知一次
```

**告警抑制（Inhibition）**：当根因告警触发时，抑制相关的派生告警

```
场景：K8s Node 宕机 → 该 Node 上的所有 Pod 也会变为不可用
如果不抑制：会同时收到 NodeDown 告警 + 几十条 PodCrashLoopBackOff 告警
```

```yaml
# Alertmanager 抑制规则
inhibit_rules:
  # 当 Node 宕机时，抑制该 Node 上的 Pod 告警
  - source_match:
      severity: 'critical'
      alertname: 'NodeDown'
    target_match:
      severity: 'warning'
      alertname: 'PodNotReady'
    # 通过 node 标签关联：Node 名匹配时抑制
    equal: ['node']

  # 当数据库不可用时，抑制所有依赖数据库的服务告警
  - source_match:
      alertname: 'MySQLDown'
    target_match:
      severity: 'warning'
      alertname: 'DependencyDown'
    equal: ['namespace']

  # 当集群整体不可用时，抑制所有组件级别告警
  - source_match:
      severity: 'critical'
      alertname: 'ClusterUnreachable'
    target_regexp:
      severity: 'critical|warning'
    equal: ['cluster']
```

**告警静默（Silence）**：在已知的维护窗口内，主动静默特定告警

```yaml
# 通过 Alertmanager API 或 amtool 添加静默
# 场景：MySQL 主从切换（计划内维护，预计 15 分钟）
# 使用 amtool 命令添加静默
# amtool silence add --duration=30m --comment="MySQL 主从切换维护" \
#   alertname="MySQLReplicationLag" severity="warning"

# 也可通过 Alertmanager Web UI 添加
# 匹配条件: alertname =~ "MySQL.*" AND severity != "critical"
# 持续: 30m
# 创建人: ops-team
# 备注: "计划内数据库维护 2026-06-09 22:00-22:30"
```

**告警依赖（Alert Dependency Chain）**：分层告警避免风暴

```
层级                  告警示例                         响应策略
─────────────────────────────────────────────────────────────
L1: 基础设施          NodeDown / DiskFull               → 基础运维
L2: 平台服务          API Server Unreachable             → 平台团队
L3: 应用服务          Order Service High Error Rate      → 应用团队
L4: 业务指标          Payment Success Rate < 95%         → 业务团队

规则：L1 触发时，抑制 L2-L4 中可推断的告警
      只有当 L1 告警确认不影响对应服务时，L2-L4 告警才独立触发
```

**告警降噪效果量化（典型生产场景）**：

| 降噪措施 | 告警量（部署前） | 告警量（部署后） | 降噪比例 |
|---------|-----------------|-----------------|---------|
| 仅告警聚合 | 5000 条/天 | 250 条通知/天 | 95% |
| 聚合 + 抑制 | 5000 条/天 | 80 条通知/天 | 98.4% |
| 聚合 + 抑制 + 静默 | 5000 条/天 | 60 条通知/天 | 98.8% |
| 全量降噪（含依赖链） | 5000 条/天 | 30-40 条通知/天 | 99.2%+ |

### On-Call 响应流程

```
告警触发
  ↓
自动通知（PagerDuty / 飞书/钉钉）
  ↓
值班工程师接收
  ├── 5 分钟内确认（Acknowledge）
  └── 未确认 → 自动升级通知到备份值班
  ↓
排查（通过日志 + 指标 + 链路）
  ↓
修复 / 降级 / 回滚
  ↓
事后：写故障复盘（Postmortem）
```

## SLO / SLI / SLA

| 术语 | 定义 | 示例 |
|------|------|------|
| **SLI** (指标) | 实际测量的服务质量指标 | 请求延迟 P99 = 120ms |
| **SLO** (目标) | 目标值或范围 | P99 延迟 < 200ms，99.9% 的月度时间 |
| **SLA** (协议) | 对外承诺，不达标则赔付 | 月度可用性 ≥ 99.99% |

**错误预算**：错误预算 = 100% - SLO。如 99.9% SLO，每月错误预算 = 43.2 分钟（30 天 × 1440 分钟 × 0.1%）。

- 错误预算未耗尽 → 可以正常发布
- 错误预算即将耗尽 → 冻结发布，优先提升稳定性
- 错误预算耗尽 → 立即停止发布，全力恢复

### SLO 工程设计：燃烧速率告警

错误预算的绝对值（剩余多少分钟）是一个静态指标，但更重要的是**消耗速度**——如果错误预算在几小时内被消耗掉 50%，即使绝对值还很多，也意味着严重问题正在发生。

**燃烧速率（Burn Rate）**：错误预算消耗速度与时间的比值。

```
燃烧速率 = 实际错误率 / SLO 允许的错误率

例如：
  - SLO = 99.9%（允许 0.1% 错误）
  - 实际错误率 = 1%
  - 燃烧速率 = 1% / 0.1% = 10x

这意味着错误预算的消耗速度是预期的 10 倍，
如果持续下去，错误预算在 1/10 的时间窗口内就会耗尽。
```

**多窗口多燃烧速率（Multi-Window, Multi-Burn-Rate）告警**：

Google SRE 的经典方法：使用两个不同时间窗口（短窗口 + 长窗口）的燃烧速率，捕捉不同严重程度的问题。

| 告警级别 | 燃烧速率 | 短窗口 | 长窗口 | 意义 |
|---------|---------|--------|--------|------|
| **P0 紧急** | 14.4x | 5 分钟 | 1 小时 | 严重问题，2 小时内耗尽预算 |
| **P1 高优先级** | 6x | 30 分钟 | 6 小时 | 严重问题，4 小时内耗尽预算 |
| **P2 警告** | 1x | 2 小时 | 1 天 | 慢速消耗，30 天内耗尽预算 |
| **P3 通知** | 0.5x | 6 小时 | 3 天 | 轻度异常，60 天内耗尽预算 |

**具体 Prometheus Rules 配置示例**：

```yaml
# SLO 燃烧速率告警规则
# 目标: HTTP 请求的可用性 SLO = 99.9%
# 定义: good / total 比率 → 错误率

groups:
  - name: slo-burn-rate-alerts
    interval: 1m
    rules:
      # 总请求量
      - record: job:http_requests:rate1m
        expr: sum(rate(http_requests_total[1m]))

      # 成功请求量
      - record: job:http_requests_good:rate1m
        expr: sum(rate(http_requests_total{status_code=~"2..|3.."}[1m])) or vector(0)

      # 实际可用性 SLI
      - record: job:sli:http_availability_1m
        expr: |
          (job:http_requests_good:rate1m / job:http_requests:rate1m) * 100

      # --- P0 紧急告警：燃烧速率 ≥ 14.4x ---
      # 短窗口 5 分钟 → 快检
      # 长窗口 1 小时 → 确认持续

      - record: job:slo_99.9:burn_rate_5m
        expr: |
          (1 - (job:http_requests_good:rate1m / job:http_requests:rate1m))
          / 0.001  # 0.1% 允许错误率

      - alert: SLO_BurnRate_P0
        expr: |
          (
            job:slo_99.9:burn_rate_5m > 14.4
          and on(job)
            job:slo_99.9:burn_rate_5m > 14.4
          )
          or
          (
            avg_over_time(job:slo_99.9:burn_rate_5m[1h]) > 14.4
          and on(job)
            avg_over_time(job:slo_99.9:burn_rate_5m[1h]) > 14.4
          )
        labels:
          severity: critical
          slo: "99.9"
        annotations:
          summary: "[P0] 错误预算正在急速消耗 (燃烧速率 > 14.4x)"
          description: |
            当前燃烧速率 {{ $value | humanize }}x，
            预计 {{ $value | humanizeDuration }} 内耗尽全部错误预算。
            需立即响应！

      # --- P1 高优先级：燃烧速率 ≥ 6x ---
      - alert: SLO_BurnRate_P1
        expr: |
          (
            avg_over_time(job:slo_99.9:burn_rate_5m[30m]) > 6
          and on(job)
            avg_over_time(job:slo_99.9:burn_rate_5m[6h]) > 6
          )
        labels:
          severity: high
          slo: "99.9"
        annotations:
          summary: "[P1] 错误预算快速消耗 (燃烧速率 > 6x)"
          description: |
            预计 {{ $value | humanizeDuration }} 内耗尽错误预算。
            请尽快排查。

      # --- P2 警告：燃烧速率 ≥ 1x ---
      - alert: SLO_BurnRate_P2
        expr: |
          (
            avg_over_time(job:slo_99.9:burn_rate_5m[2h]) > 1
          and on(job)
            avg_over_time(job:slo_99.9:burn_rate_5m[1d]) > 1
          )
        labels:
          severity: warning
          slo: "99.9"
        annotations:
          summary: "[P2] 错误预算缓慢消耗 (燃烧速率 > 1x)"
          description: |
            按当前速度，预计 {{ $value | humanizeDuration }} 内耗尽错误预算。
            请关注趋势。
```

**燃烧速率告警的优势**：
- **提前发现**：不等错误预算耗尽才告警，在消耗速度异常时立即通知
- **精确分级**：不同燃烧速率映射不同告警优先级，避免 P0 泛滥
- **双重验证**：短窗口检测 + 长窗口验证，既快又准，减少误报
- **自适应的通知频率**：严重程度高的告警通知更频繁，低严重度的减少通知

## 生产案例：某 SaaS 公司从 ELK 迁移到 Loki + Mimir 的成本优化

### 业务背景

**公司画像**：
- 面向企业的 SaaS 平台（CRM + ERP），约 5000 家企业客户
- 200+ 微服务，部署在 3 个 AWS 区域
- 日 API 请求量约 3 亿，每日日志产生量约 1.6TB（月累计 ~50TB）
- 团队规模：基础架构团队 15 人，SRE 团队 8 人

### 原始架构与痛点

**原始架构（ELK Stack）**：

```
应用服务 → Filebeat → Logstash → Elasticsearch (30 节点集群)
                                   ├── 数据节点: 24 x r5.2xlarge (SSD 2TB/节点)
                                   ├── 协调节点: 4 x c5.2xlarge
                                   └── 主节点: 2 x t3.medium
指标 → Prometheus Server (单机) → Thanos (S3 长期存储)
```

**月度成本明细**：

| 项目 | 费用/月 | 占比 |
|------|---------|------|
| ES 集群（30 节点 r5.2xlarge） | $24,000 | 68.6% |
| SSD 存储（ES 数据盘） | $6,500 | 18.6% |
| Logstash 集群（4 节点） | $2,000 | 5.7% |
| 网络流量（跨 AZ 传输） | $1,500 | 4.3% |
| Thanos (Sidecar + S3) | $1,000 | 2.8% |
| **合计** | **$35,000** | **100%** |

**痛点分析**：

| 痛点 | 具体表现 | 严重程度 |
|------|---------|---------|
| 存储成本高 | 30 节点 ES 集群，日增 1.6TB，SSD 成本极高 | 🔴 最严重 |
| 长周期查询慢 | 查询 3 天前的日志，响应时间 > 30s，7 天以上数据基本不可查 | 🔴 严重 |
| 日志索引膨胀 | 非结构化日志导致倒排索引膨胀，实际日志数据仅占 30%，索引占 70% | 🔴 严重 |
| 运维负担重 | ES 集群维护频繁，分片均衡、GC 调优、滚动重启每周至少 1 次 | 🟡 中 |
| 指标存储瓶颈 | Thanos 组件过多（Sidecar + Store + Compactor + Querier + Ruler），排错复杂 | 🟡 中 |

### 架构方案设计

**迁移目标**：
1. 月度日志存储成本降低 60% 以上
2. 保持 30 天内的日志查询响应 < 5s
3. 实现 365 天日志保留
4. 减少运维工作量

**选型过程（评估方案）**：

| 候选方案 | 成本 | 查询性能 | 运维复杂度 | 结论 |
|---------|------|---------|-----------|------|
| ELK 集群优化（冷热分层） | $20,000/月 | 优（全文搜索） | 中 | 成本仍较高 |
| Loki + Mimir | $8,000/月 | 良（标签搜索，非全文搜索） | 低 | ✅ 推荐 |
| ClickHouse | $6,000/月 | 优（列式存储） | 高（需自建） | 运维成本高 |
| S3 + Athena 查询 | $5,000/月 | 差（分钟级查询） | 低 | 查询延迟不可接受 |

**最终方案（Grafana Loki + Grafana Mimir）**：

```
应用服务 → Promtail (Loki 日志采集)
              |                     → Grafana (统一查询面板)
指标 → Prometheus → Grafana Mimir (兼容 Prometheus API)
                         |
                    S3 对象存储 (长期保留)
```

### 实施细节

**第一阶段：日志迁移（Loki）**

```
迁移步骤：
1. 搭建 Loki 集群 (3 个读写节点 + 3 个后端节点，c5.xlarge)
2. 所有服务安装 Promtail 替代 Filebeat
3. 并行双写 2 周（ES + Loki）
   └── 验证数据一致性，团队熟悉 Loki LogQL 查询语法
4. 切换只读流量到 Loki，ES 保留为只读备份
5. 30 天后下线 ES 集群
```

**Loki 关键配置**：

2. 配置 Prometheus remote_write 到 Mimir
3. 双写 1 周（Thanos + Mimir 并存）

| 指标 | 迁移前（ELK + Thanos） | 迁移后（Loki + Mimir） | 改善幅度 |
|------|----------------------|----------------------|---------|

### 经验教训

**做对了的事**：

1. **并行双写过渡**：2 周双写期保证了数据零丢失，团队有空学习 Loki 的 LogQL 语法
2. **标签体系与 Prometheus 对齐**：日志标签复用已有的 Prometheus Label 体系（service, env, namespace），查询路径统一
3. **日志保留分层实施到位**：热数据 7 天 SSD，温数据 30 天 HDD，冷数据 365 天 S3，自动迁移无需人工干预
4. **Mimir 替代 Thanos 后组件数从 6 个减到 1 个**：运维负担显著下降

**踩过的坑**：

1. **高基数标签爆炸**：最初将 `user_id` 设为 Loki Label，导致索引写入瓶颈。修复：`user_id` 改放在日志内容字段，不设索引
2. **LogQL 学习曲线**：从 Kibana 的 Lucene 语法切换到 LogQL，团队花了约 2 周才熟练。建议：提前组织 LogQL 培训
3. **复杂文本搜索问题**：Loki 的 `|~ "regex"` 过滤在大数据量下性能大幅下降。对于合规审计场景的复杂全文搜索，保留了小规模 ES 集群（3 节点）做专项支持
4. **Promtail 资源占用**：首次部署时未限制 Promtail 资源，部分节点的 Promtail 消耗了 1GB+ 内存。修复：设置 `limits: memory: 256Mi` + 限制与 K8s Pod 数量相关的采集上限

**总结原则**：

```
不是所有日志都需要全文搜索能力！
  ├── 80% 的运维场景 → 标签搜索（Loki）就够了
  │   ├── 错误排查 → service + level + error_code 标签
  │   ├── 性能分析 → service + duration_bucket 标签
  │   └── 安全审计 → 低频，可接受几分钟延迟
  └── 20% 的复杂场景 → 保留小规模 ES
      ├── 全文模糊搜索
      ├── 合规数据挖掘
      └── 业务团队的广告词搜索等
```

**后续改进方向**：
- 引入 OpenTelemetry Collector 统一数据采集，替代 Promtail
- 对 INFO 级别日志启用 1% 采样，预计节省额外 20% 存储
- 探索 Mimir 的连续性验证（Continuous Validation）功能，自动检测指标数据质量问题
