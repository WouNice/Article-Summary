# 第4章：持续交付与部署策略

## 本章学习目标

- 区分持续交付与持续部署的概念边界
- 掌握多种部署策略的原理、选型与取舍
- 理解功能开关如何实现"部署与发布分离"
- 能够为业务场景设计合理的发布方案

## 从 CI 到 CD 的演进

### 概念辨析

```
持续集成 (CI)
  ↓ 代码合并后自动构建 + 测试
持续交付 (CD - Continuous Delivery)
  ↓ 代码始终处于可部署状态 → 手动触发部署
持续部署 (CD - Continuous Deployment)
  ↓ 通过测试的代码自动部署到生产环境
```

| 概念 | 自动化程度 | 线上部署 | 代表公司 |
|------|-----------|---------|---------|
| 持续集成 | 构建 + 测试自动化 | 人工触发 | 大多数团队 |
| 持续交付 | CI + 准备好部署 | 人工确认后自动部署 | Amazon, Netflix |
| 持续部署 | 全自动 | 自动推送到生产 | Etsy, Flickr |

### 部署流水线的目标

> **每一行代码提交都应触发一次"安全到生产"的验证过程。**

```
代码提交 → CI → 部署到测试环境 → 验收测试 → 部署到预发布 → 生产部署
                ↑______________ 每个阶段自动化，只有生产部署可以可选手动 ________↓
```

## 主流部署策略全景

👉 **详细策略说明** 见同目录下的 [代码发布方式总结.md](./代码发布方式总结.md)，本章重点从**选型决策**和**实践要点**角度深化。

### 滚动部署

```
旧版本 ──●──●──●──●──●──●──
               ↓ 逐个/分批替换
新版本 ──●──●──●──●──●──●──
```

**实践要点**：
- 批次大小需合理（小型服务 20%，核心服务 10%）
- 确保接口向前/向后兼容（新旧实例共存）
- 配合健康检查（Health Check）逐批推进
- 设置回滚阈值：失败率达到 X% 时自动暂停

### 蓝绿部署

```
           ┌──────────┐
用户 ──→   │  LB/Router│──→ 蓝环境（当前线上）
           └──────────┘──→ 绿环境（新版本）
```

**实践要点**：
- 数据库兼容：Schema 变更需向前兼容或双写
- 流量切换时间窗口：充分考虑连接 Drain
- 蓝环境保留：回滚只需切回，无需重新部署
- 成本优化：用云资源按需创建绿环境

### 金丝雀发布

```
           ┌──────────┐──→ 旧版本 (90% 流量)
用户 ──→   │  Gateway  │
           └──────────┘──→ 新版本 (10% 流量)
                           ↓ 监控指标正常
                          新版本 (30% → 60% → 100% 逐步扩量)
```

**实践要点**：
- 流量路由：基于 Header / Cookie / IP 哈希
- 监控关键指标：错误率、延迟 P95/P99、业务指标
- 自动回滚：指标异常时自动缩回金丝雀
- 渐进策略：10% → 30% → 60% → 100%（每阶段观察 5~15 分钟）

### 功能开关

这是**最灵活的发布方式**，在代码中预埋开关：

```python
# 示例：功能开关
if feature_flag.is_enabled("new_checkout_flow", user_id):
    return new_checkout_flow(request)
else:
    return old_checkout_flow(request)
```

**部署与发布分离**：

```
部署（Deploy）：       新代码上线，功能默认关闭
                       ↓
发布（Release）：      逐步打开功能开关，控制用户群
                       ↓
紧急关停：             关闭开关，无需回滚
```

**功能开关平台**：LaunchDarkly、FeatBit、Unleash，或自建

### 部署策略选型决策树

不同业务场景对部署策略的核心诉求不同。以下决策步骤帮助从关键约束出发快速定位最优策略。

**决策步骤**

```
Step 1：是否有零停机要求？
  ├── 是 → 排除滚动部署（有短暂停机窗口）
  └── 否 → Step 2

Step 2：是否资源敏感（需要最小化额外基础设施成本）？
  ├── 是 → 选择滚动部署
  └── 否 → Step 3

Step 3：是否需要灰度验证或逐步开放？
  ├── 是 → Step 4
  └── 否 → Step 5

Step 4：需要多细粒度的灰度控制？
  ├── 按用户/流量百分比 → 金丝雀发布
  └── 按功能特性维度 → 功能开关

Step 5：回滚速度是否关键？
  ├── 是 → 蓝绿部署（环境保留，秒级切换）
  └── 否 → 滚动部署或不可变部署
```

**场景 × 策略匹配矩阵**

| 业务场景 | 推荐策略 | 备选策略 | 决策依据 |
|---------|---------|---------|---------|
| 内部管理系统 | 滚动部署 | 蓝绿部署 | 对停机不敏感，资源成本优先 |
| 电商核心交易 | 金丝雀发布 | 蓝绿部署 | 需要灰度验证，同时保障回滚能力 |
| API 网关/中间件 | 蓝绿部署 | 金丝雀 | 回滚速度优先，资源足够 |
| 移动端后端 | 功能开关 + 金丝雀 | 蓝绿部署 | 需要按 App 版本控制 |
| 数据库 Schema 变更 | 滚动部署 + 功能开关 | 金丝雀发布 | Schema 兼容性制约，需分阶段 |
| ToB 企业应用 | 蓝绿部署 | 滚动部署 | 客户对停机敏感，回滚承诺要求高 |
| 金融/合规系统 | 功能开关 + 金丝雀 + 蓝绿 | 多层策略组合 | 合规要求分层验证 |
| Serverless 函数 | 不可变部署（Alias 切换） | 金丝雀 | 平台原生支持版本管理 |

**策略组合模式**

单一策略往往无法满足所有需求，实际生产中是多种策略的组合：

| 组合模式 | 适用场景 | 典型技术栈 |
|---------|---------|-----------|
| 功能开关 + 滚动部署 | 资源优先，但有特性维度控制需求 | Feature Flag SDK + K8s Deployment |
| 功能开关 + 金丝雀 | 需要细粒度灰度，且有基础设施支撑 | LaunchDarkly + Istio/Envoy |
| 金丝雀 + 蓝绿 | 既需要灰度验证，又需要秒级回滚 | Istio VirtualService + 双套环境 |
| 功能开关 + 蓝绿 | 复杂业务逻辑 + 强合规要求（金融级） | Unleash + 蓝绿 K8s Namespace |

### 部署策略成本分析

不同部署策略对基础设施、资源利用率、运维人力有显著差异。

**资源成本对比**

| 策略 | 资源消耗倍数 | 额外基础设施 | 说明 |
|------|------------|-------------|------|
| 滚动部署 | 1.0× | 无 | 复用相同资源池，分批替换 |
| 金丝雀发布 | 1.1×~1.3× | 金丝雀实例 + 流量路由组件 | 额外保留少量旧版本（或新版本）实例 |
| 不可变部署 | 1.0×~1.5× | 镜像仓库 + 版本管理 | ASG 替换实例，短暂双倍 |
| 蓝绿部署 | 2.0× | 双倍资源 + 流量切换组件 | 发布期间两套环境同时运行 |
| 混合组合 | 2.0×~3.0× | 多种基础设施 | 按需创建，发布后释放 |

**详细成本估算（以 50 个 Pod 的微服务为例，月基准 $10,000）**

| 策略 | 日常资源成本 | 发布期间额外成本 | 运维成本 | 月总成本估算 | 回滚人力成本 |
|------|------------|----------------|---------|------------|------------|
| 滚动部署 | $10,000 | $0（无额外资源） | 低 | $10,000 | 高（回滚需要重新部署） |
| 蓝绿部署 | $10,000~$13,000 | $3,000~$5,000/月（绿环境保持） | 中 | $13,000~$18,000 | 低（秒级切换） |
| 金丝雀发布 | $10,000~$11,000 | $500~$1,000（金丝雀额外资源） | 中 | $10,500~$12,000 | 低（自动缩回） |
| 功能开关 + 金丝雀 | $10,000~$11,500 | $1,000~$2,500（FF 平台 + 额外资源） | 中高 | $11,000~$14,000 | 极低（关闭开关即可） |

**流量管理基础设施成本**

| 组件 | 用途 | 成本（月估） | 技术选型 |
|------|------|------------|---------|
| Service Mesh (Istio/Linkerd) | 灰度路由、流量拆分、熔断 | $500~$2,000（控制面资源） | 需要 K8s 集群支撑 |
| API Gateway (Kong/APISIX) | 金丝雀 Header/Cookie 路由 | $200~$1,000 | 可独立部署，不需要 Mesh |
| 云服务 ALB/NLB | 蓝绿切换、权重路由 | $100~$500 | 云厂商原生，零运维 |
| Feature Flag 服务平台 | 功能开关控制台 + SDK | $0~$1,500 | Unleash 开源免费，LaunchDarkly 商业收费 |
| DNS 切换 | 环境间全局切换 | $0~$100 | 需要 TTL 配合，有传播延迟 |

**成本-收益权衡决策表**

| 如果公司状况是... | 建议策略 | 不推荐 | 理由 |
|------------------|---------|-------|------|
| Startup，预算紧张 | 滚动部署 + 最小化功能开关 | 蓝绿部署 | 基础设施成本是第一约束 |
| 中型 SaaS，关注用户体验 | 金丝雀发布 + 功能开关 | 纯滚动部署 | 灰度验证成本远小于线上事故损失 |
| 大型平台，合规要求高 | 蓝绿部署 + 功能开关 + 多层审批 | 单一策略 | 回滚能力和合规优先级高于成本 |
| 金融级，零事故容忍 | 功能开关 + 金丝雀 + 蓝绿 | 滚动部署 | 安全优先，预留 3 倍资源预算 |

### 数据库变更与部署策略的兼容性分析

数据库 Schema 变更是发布过程中最容易被忽视的风险点。"不兼容的数据库变更" 是导致生产事故的首因之一。

**数据库变更的兼容性等级**

| 兼容等级 | 类型 | 示例 | 是否可向前兼容 |
|---------|------|------|-------------|
| ✅ 安全（完全兼容） | 新增列（可空/有默认值） | `ALTER TABLE users ADD COLUMN nickname VARCHAR(100) DEFAULT ''` | ✅ |
| ✅ 安全（完全兼容） | 新增索引 | `CREATE INDEX idx_users_email ON users(email)` | ✅ |
| ⚠️ 有风险（需注意事项） | 新增 NOT NULL 列 | `ALTER TABLE orders ADD COLUMN ` `status` ` TINYINT NOT NULL DEFAULT 0`（需注意大表锁） | ✅（有默认值） |
| ⚠️ 有风险（需双写） | 列重命名 | `ALTER TABLE users CHANGE name username VARCHAR(100)` | ❌（旧代码写 name 会失败） |
| ⚠️ 有风险（需双写） | 列类型变更 | `ALTER TABLE products MODIFY price DECIMAL(12,2)` | ⚠️（取决于变更方向） |
| ❌ 不兼容 | 删除列 | `ALTER TABLE users DROP COLUMN old_field` | ❌ |
| ❌ 不兼容 | 拆分表 | 将 `users` 表拆分为 `users` + `profiles` | ❌ |
| ❌ 不兼容 | 修改存储过程签名 | 改变参数个数或类型 | ❌ |

**各部署策略对数据库变更的兼容性**

| 部署策略 | 不兼容 Schema 变更 | 兼容 Schema 变更 | 最佳做法 |
|---------|------------------|-----------------|---------|
| 滚动部署 | ❌ 新旧实例共存，旧代码读不到新列会失败 | ✅ 分阶段 Apply 迁移 | 先加列（可空），再写代码，再 Not Null |
| 蓝绿部署 | ❌ 切换瞬间可能造成数据不一致 | ✅ 蓝绿共用同一 DB 时可向前兼容 | 将 Schema 变更放在切换前独立执行 |
| 金丝雀发布 | ⚠️ 新旧代码路由到同一 DB，不兼容变更会破坏旧实例 | ✅ 在前置阶段单独执行迁移 | 数据库迁移作为 CI 流水线独立阶段 |
| 功能开关 | ⚠️ 如果旧代码路径仍会访问变更后的表 | ✅ 新代码路径引用新 Schema | 用 Flag 保护新 Schema 的访问代码 |

**数据库变更的最佳实践（分步策略）**

以"将 `users.name` 拆分为 `first_name` + `last_name`"为例，这通常需要 4 个发布周期：

```
发布周期 1：新增列 + 双写
  - 新增 first_name, last_name 列（可空）
  - 修改写操作：同时写入 name, first_name, last_name
  - 运行后台任务：将所有 name 拆分填充到 first_name, last_name

发布周期 2：读取切换
  - 修改读操作：从 first_name, last_name 读取
  - 老字段 name 仍作为后备

发布周期 3：清理 name 字段
  - 确认 first_name, last_name 数据完整
  - 移除所有对 name 字段的读写引用
  - 可选：DBA 清理 name 列

发布周期 4（可选）：删除列
  - 如果已确认无引用，ALTER TABLE DROP COLUMN name
  - 这个过程可能需要更长时间观察
```

**数据库变更的部署策略兼容矩阵**

| 策略 | 零停机 | 新旧实例兼容 | 回滚 DB 兼容 | 推荐度 |
|------|-------|------------|------------|-------|
| 滚动部署 | ❌（短暂不可用） | ✅（需要向前兼容） | ⚠️（需编写 revert migration） | ⭐⭐⭐ |
| 蓝绿部署 | ✅（切换瞬间） | ✅（切换前验证绿环境） | ✅（蓝环境保留原 Schema） | ⭐⭐⭐⭐ |
| 金丝雀发布 | ✅（逐步切换） | ✅（金丝雀实例跑新代码） | ✅（金丝雀缩回即可） | ⭐⭐⭐⭐ |
| 功能开关 | ✅（按 Flag 控制） | ✅（Flag 关闭时走旧代码） | ✅（关闭 Flag，无需 DB 回滚） | ⭐⭐⭐⭐⭐ |

**关键规则**

1. **数据库迁移必须是前向兼容的**——旧版本代码在新 Schema 上也能正常工作
2. **不要在一次发布中同时做不兼容 Schema 变更 + 代码重构**——风险叠加
3. **大表 DDL 需谨慎**——MySQL 的 ALTER TABLE 可能锁表，建议用 pt-online-schema-change (Percona Toolkit)
4. **数据库回滚比代码回滚更难**——代码可以一秒回滚，数据库迁移回滚需要逆向脚本，且涉及数据完整性
5. **使用数据库迁移工具管理版本**——Flyway (Java), Liquibase (Java), Alembic (Python), goose (Go)

### 渐进式交付（Progressive Delivery）

**渐进式交付** 是将功能开关、金丝雀发布、指标驱动的自动回滚整合在一起的高级发布模式。它不仅是技术策略，更是一种发布文化——把风险控制从"发布后检查"前移到"发布中持续验证"。

**渐进式交付的核心理念**

```
传统发布：
  准备 → 部署 → 祈祷 → 发现 bug → 紧急回滚

渐进式交付：
  代码上线（功能默认关闭）
    → 内部白名单验证（0.1%）
      → 外部小流量金丝雀（1%）
        → 自动监控指标
          → 逐步扩量（10% → 25% → 50% → 100%）
            → 全量开放
              → 如有异常，自动缩回 + 告警
```

**三要素整合**

```
渐进式交付 = 功能开关                + 金丝雀发布      + 指标驱动自动回滚
              │                         │                   │
              ▼                         ▼                   ▼
          按用户/特性维度          按流量百分比           基于指标阈值
          的细粒度控制            的逐步扩量              的自动化安全网
```

**典型架构**

```
                         ┌──────────────────┐
                         │  Feature Flag    │ ← 按用户/特性/环境控制
                         │  Platform        │   功能的可见性
                         │  (Unleash/FF SDK)│
                         └───────┬──────────┘
                                 │ Flag 状态
                                 ▼
 用户请求 →  API Gateway ─→  Sidecar (Istio Envoy)
             │                  │
             │          ┌───────┴───────┐
             │          │ 金丝雀权重路由 │
             │          └───────┬───────┘
             │                  ▼
             │          ┌──────────────────┐
             │          │  新版本实例池     │
             │          │  (x% 流量)       │
             │          └───────┬──────────┘
             │                  │ 指标数据
             │          ┌───────▼──────────┐
             │          │  监控系统         │ ← 自动判定：错误率 > 0.5%？
             │          │  (Prometheus +   │   P99 延迟 > 500ms？
             │          │   Alertmanager)  │  5XX > 1%
             │          └───────┬──────────┘
             │                  │ 决策
             │          ┌───────▼──────────┐
             │          │ 自动回滚触发器    │ → 关闭 Flag / 缩回金丝雀
             │          └──────────────────┘
```

**指标驱动的自动回滚**

```yaml
# 渐进式交付的自动回滚规则示例（Prometheus 告警规则）
groups:
  - name: progressive-delivery
    rules:
      - alert: CanaryErrorRateHigh
        expr: |
          rate(http_requests_total{version="canary", status=~"5.."}[5m])
          /
          rate(http_requests_total{version="canary"}[5m])
          > 0.01
        for: 2m
        labels:
          severity: critical
          auto_rollback: "true"
        annotations:
          summary: "金丝雀版本错误率超过 1%，触发生自动回滚"

      - alert: CanaryLatencyHigh
        expr: |
          histogram_quantile(0.99,
            rate(http_request_duration_seconds_bucket{version="canary"}[5m])
          ) > 0.5
        for: 3m
        labels:
          severity: warning
          auto_rollback: "true"
        annotations:
          summary: "金丝雀版本 P99 延迟超过 500ms，触发生自动回滚"
```

**渐进式交付的阶段定义**

| 阶段 | 发布范围 | 验证重点 | 持续时间 | 自动推进条件 |
|------|---------|---------|---------|------------|
| Stage 0: 部署 | 0% 用户（代码上线+Flag关闭） | 系统健康（无 Crash） | 5 分钟 | 部署成功 + Health Check 通过 |
| Stage 1: 内部验证 | 内部/白名单用户（0.1%） | 功能正确性、关键链路 | 15~30 分钟 | 错误率 < 0.1%, P99 < 200ms |
| Stage 2: 小范围验证 | 1%~5% 外部用户 | 用户体验、性能基线 | 30~60 分钟 | 错误率 < 0.5%, P99 < 300ms |
| Stage 3: 中等范围 | 10%~30% | 综合指标、业务指标 | 1~2 小时 | 无目标告警、业务指标正常 |
| Stage 4: 大范围 | 50%~100% | 全量验证、容量评估 | 1~2 小时 | 无目标告警 |
| Stage 5: 放量完成 | 100% + Flag 全开 | 持续监控 24~72h | 24~72 小时 | 指标稳定、无回滚触发 |

**渐进式交付的工具链**

| 工具类型 | 推荐工具 | 说明 |
|---------|---------|------|
| Feature Flag | LaunchDarkly, Unleash, FeatBit | 细粒度开关控制和用户分段 |
| 流量路由 | Istio, Envoy, Kong | 按 Header/Cookie/IP 权重分发 |
| 指标监控 | Prometheus + Grafana | 实时采集和可视化 |
| 自动回滚 | Flagd + Keptn + Flagger | Kubernetes 原生渐进式交付 |
| 全局发布编排 | Argo Rollouts, Flagger | 支持自动推进/回退的金丝雀发布 |

| 指标 | 传统金丝雀 | 渐进式交付 |

### 部署策略编排

一个成熟的发布可能是多模式组合的：

```
阶段1：功能开关部署 —— 代码上线但功能关闭
阶段2：金丝雀发布   —— 5% 流量验证系统稳定
阶段3：渐进扩量     —— 30% → 60% → 100%

同时：蓝绿环境准备就绪，随时全量回滚
```

## 发布工程最佳实践

### 构建产物不变性

> **一次构建，多次部署（Build Once, Deploy Anywhere）**

- 在 CI 中构建一次，生成不可变制品
- 同一制品经过 Dev → Staging → Production 全部环境
- 避免每个环境重新构建（"我一不小心改了点东西"的风险）

### 部署前安全检查清单

```
□ 制品 Hash 与 CI 构建一致（无中间修改）
□ 依赖扫描通过（无 CVE）
□ 配置与密钥已注入（非硬编码）
□ 数据库迁移已验证兼容
□ 预发布 Smoke Test 通过
□ 监控告警已配置
□ 回滚方案已确认
□ 相关干系人已通知
```

### 部署后验证

```yaml
# Post-deploy verification checklist
steps:
  - name: Health Check
    run: curl -f http://service/healthz

  - name: Smoke Test
    run: ./smoke-test.sh

  - name: Metrics Verification
    run: |
      # 对比部署前后5分钟的 error rate
      check_error_rate --baseline 5min --now 5min

  - name: Auto Rollback Condition
    run: |
      if [ error_rate > threshold ]; then
        trigger_rollback()
      fi
```

## 生产案例：金融级应用的多层发布策略编排

### 业务背景

**公司**：信安金融科技（XinAn FinTech），持牌互联网小贷平台
**规模**：技术团队约 150 人，平台日交易流水约 2 亿元
**监管要求**：
- 银保监会《商业银行互联网贷款管理暂行办法》要求：所有系统变更需有完整审批记录
- 央行《金融科技发展规划》要求：对客服务变更必须经过至少 3 级审批
- 行业合规要求：变更必须有可审计的发布记录和回滚方案
- PCI DSS 合规：代码变更必须经过安全审计

**痛点**：

1. **审批流程冗长**：每次发布需要经过开发组长 → 技术经理 → 合规审核 → 安全审核 → CTO 最终确认，平均审批周期 2~3 天
2. **业务压力大**：P2P 转型助贷后，业务方要求每周至少 2 次版本更新，但合规流程只能支持每周 1 次
3. **回滚风险高**：曾经有一次 SQL Schema 变更导致回滚时需要数据修复，花了两天时间
4. **审计追踪不足**：传统的发布记录在多个系统间散落（Jira + Jenkins + 审批流），审计人员检查一次需要 3 天

### 架构设计方案

**核心策略：功能开关 + 金丝雀 + 蓝绿环境的三层组合策略。**

#### 架构总览

```
                           ┌──────────────────────────────┐
                           │   发布编排引擎 (Argo Workflows) │
                           │   + 审批流集成 (Jira + 企微)    │
                           └──────┬───────────────┬───────┘
                                  │               │
                    ┌─────────────▼───────┐   ┌───▼────────────┐
                    │  Feature Flag 平台   │   │    蓝绿环境      │
                    │  (自建 Unleash)     │   │  (K8s Namespace) │
                    │  - 按用户/角色/时间  │   │  蓝: 当前生产    │
                    │  - 环境级开关       │   │  绿: 新版本环境  │
                    └─────────────────────┘   └────────────────┘
                                                       │
                    ┌──────────────────────────────────▼────┐
                    │          流量路由 (Istio Gateway)      │
                    │  - 金丝雀权重路由                      │
                    │  - 用户分组 Header 路由                │
                    │  - 内部白名单 Cookie 路由              │
                    └───────────────────────────────────────┘
```

### 实施细节：5 阶段发布流程

```
┌────────────────────────────────────────────────────────────────┐
│ Stage 1: Feature Flag 关闭部署                                  │
│   - 代码部署到绿环境（新版本）                                    │
│   - 所有新功能默认 Feature Flag = OFF                          │
│   - 即使绿环境流量意外接入，用户无感知                           │
│   - 持续时间：10 分钟（仅部署时间）                              │
│   - 安全网：绿环境独立 K8s Namespace，未接入流量                 │
└────────────────────────────┬───────────────────────────────────┘
                             │
┌────────────────────────────▼───────────────────────────────────┐
│ Stage 2: 内部白名单金丝雀（1% 流量）                             │
│   - 内部员工 + 测试账号自动路由到绿环境                          │
│   - 通过 Unleash 白名单分组控制                                 │
│   - 监控指标：错误率、P99 延迟、关键业务流程成功率                │

│   - 安全网：任一指在异常 → Istio 自动切回蓝环境                  │

└────────────────────────────┬───────────────────────────────────┘
                             │
┌────────────────────────────▼───────────────────────────────────┐
│ Stage 3: 外部用户金丝雀（5%）                                   │
│   - 随机选择 5% 外部用户流量路由到绿环境                         │
│   - 开启 Istio 权重路由（95:5）                                 │
│   - 监控业务级指标：下单成功率、支付成功率、用户投诉率            │
│   - 持续时间：1~2 小时                                         │
│   - 安全网：自动缩回 + 告警通知到企微群                         │
│   - 审批：无需额外审批（CI/CD 管道已包含合规检查）                │
└────────────────────────────┬───────────────────────────────────┘
                             │
┌────────────────────────────▼───────────────────────────────────┐
│ Stage 4: 渐进扩量（30% → 60% → 100%）                           │
│   - 30% → 观察 30 分钟                                        │
│   - 60% → 观察 30 分钟                                        │
│   - 100% → 观察 1 小时（全部流量进入绿环境）                    │
│   - 每一步都需要 Prometheus 指标验证 + 自动检查                │
│   - 安全网：任一步指标异常 → 自动缩回至 5%，触发 CTO 告警       │
│   - 审批：扩容到 60% 前需技术经理 + 合规在线审批（企微飞书）     │
└────────────────────────────┬───────────────────────────────────┘
                             │
┌────────────────────────────▼───────────────────────────────────┐
│ Stage 5: 蓝绿环境保留（72 小时快速回滚窗口）                     │
│   - 蓝环境保留 72 小时，不回收                                 │
│   - 不可同时启用蓝/绿两套环境写入同一数据库                     │

│   - 72 小时后：蓝环境释放资源，绿环境正式成为"新蓝环境"          │
```

### 经验教训

1. **合规不是速度的敌人**：在合规框架内做自动化审批流才是最难的工程挑战。与合规部门合作定义"不需要人工审批的变更类型"，将 80% 的变更从审批流程中解放出来，仅保留高风险变更需要人工审批
2. **数据库变更策略是生命线**：金融级系统最危险的不是代码 bug，而是不可恢复的数据问题。必须严格遵守前向兼容原则，每个 Schema 变更都需要编写回滚脚本，并经过 DBA 审查
3. **自动回滚要有"人工覆盖"**：自动回滚是安全网但不是万能药。某些回滚场景可能需要人工判断，例如大促期间自动回滚可能比继续运行更危险。设置"自动回滚窗口期"和"人工决策窗口"
4. **审计日志不只是合规要求，也是排障工具**：每次发布的完整日志（谁、何时、做了什么、为什么）不仅满足合规要求，也是事后排障和持续改进的重要数据源
5. **Feature Flag 需要生命周期管理**：长期开启/不清理的 Flag 会导致代码腐化（Conditional Complexity）。建立 Flag 清理机制——功能稳定运行 2 周后自动删除 Flag 代码
6. **Staging 环境要与生产"足够像"但不能完全相同**：有些问题（如数据量级不同导致的查询性能差异）只能在生产金丝雀阶段发现，不要期望 Staging 能发现所有问题
7. **渐进式交付是文化变革，不只是技术选型**：需要让整个团队（包括 PM、QA、合规）理解并信任这套机制，才能充分发挥其价值。最有效的推广方式是在一次实际事故中展示"渐进式交付如何阻止了灾难"

## 本章小结

| 要点 | 说明 |
|------|------|
| CI → CD 演进 | 持续集成 → 持续交付（手动部署）→ 持续部署（全自动） |
| 部署策略 | 滚动（资源友好）、蓝绿（快速回滚）、金丝雀（灰度验证）、不可变（一致性高）、功能开关（部署发布分离） |
| 选型决策 | 根据零停机、资源限制、灰度需求、回滚速度依次缩小选型范围 |
| 策略组合 | 实际生产往往是多种策略的组合使用 |
| 成本分析 | 蓝绿双倍资源，金丝雀适量增加，功能开关最灵活；需平衡成本和风险 |
| 数据库兼容 | Schema 变更必须前向兼容，避免与代码变更叠加风险 |
| 渐进式交付 | 功能开关 + 金丝雀 + 指标驱动自动回滚三合一，实现发布全流程自动化安全网 |
| 不可变制品 | 一次构建多次部署，消除环境差异 |
| 验证闭环 | 部署前后都要有自动化验证和回滚触发条件 |
| 功能开关 | 实现部署与发布解耦，降低上线风险 |
| 生产案例 | 信安金融 5 阶段发布策略实现部署前置时间从 3 天降到 4 小时 |
