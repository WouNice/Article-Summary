## 混沌工程：为什么要主动破坏

### 定义

> **混沌工程（Chaos Engineering）** 是通过在生产环境或类生产环境中有计划地引入故障，来验证系统在异常条件下的行为，从而主动发现脆弱性并提升系统韧性的学科。

### 核心思想

```
传统测试："这个系统，我希望它在一切正常时表现良好。"
混沌工程："这个系统，我想知道它在出了问题时会变成什么样子。"
```

### 为什么要主动引入故障

两个现实：

1. **故障不可避免**——硬盘会坏、网络会断、依赖会挂、流量会突增
2. **系统复杂度已经超越了任何人的理解**——没有人能完全预测分布式系统在故障下的行为

**混沌工程的核心洞见**：

> 与其等到真实故障发生时被动应对，不如主动、有计划地制造故障，提前发现盲点。

## 混沌工程四大原则（来自 Principles of Chaos Engineering）

### 原则一：定义稳态

实验前明确系统的"正常行为"——即如何度量系统"健康"。

```yaml
# 稳态定义示例
steady_state:
  metrics:
    - http_errors.rate < 0.01  # 错误率 < 1%
    - p99_latency < 500ms      # P99 延迟 < 500ms
    - order_success.rate > 99.5%  # 业务成功率
```

### 原则二：假设稳态会保持

实验的假设是：引入的故障**不会**违背稳态指标。

```
假设："当 order-service 实例减少一半时，"
      "错误率仍 < 1%，P99 延迟仍 < 500ms。"
```

### 原则三：在生产环境中验证

- 类生产环境已经"太干净"了
- 真实流量模式、真实数据量和真实用户行为无法完美模拟
- 混沌实验的使用范围：**先在测试环境演练 → 逐步扩大范围到预发布 → 最终在生产环境运行"

### 原则四：自动化实验

手动跑混沌实验不可扩展。通过自动化平台持续运行实验，形成常态化机制。

## 混沌实验设计方法

### 实验周期

```
┌─────────┐  ┌──────────┐  ┌────────┐  ┌──────────┐
│ 假设   │→ │ 实验设计  │→ │ 执行   │→ │ 分析结果  │
│ 定义   │  │ 最小爆破  │  │ 监控   │  │ 改进系统  │
└─────────┘  └──────────┘  └────────┘  └──────────┘
                                          │
                                          └────────→ 新假设 → 下一轮
```

### 实验设计模板

```yaml
# 混沌实验模板
实验名称: Kill Random Pod in Order Service
假设: 当 order-service 的 1 个 Pod 被杀死时，
      Stable metrics (错误率 < 1%) 不会受到影响。
方法: 随机选择 1 个 order-service Pod，执行删除。
监控: 错误率、P99 延迟、成功率，持续 5 分钟。
爆炸半径: 仅影响非核心用户请求。
停止条件: 错误率 > 5% 或延迟 > 2s 时自动回滚。
```

### 爆炸半径控制（最重要的事！）

| 等级 | 影响范围 | 适合场景 | 实验类型 |
|------|---------|---------|---------|
| L1 | 单 Pod | 初步验证 | Kill Pod |
| L2 | 部分副本 | 验证熔断降级 | Kill 30% replicas |
| L3 | 完整服务 | 验证容灾 | Kill all replicas of one AZ |
| L4 | 跨服务影响 | 验证级联故障 | Kill upstream + mock behavior |
| L5 | 全局 | 大演练 | Region 故障模拟 |

> **规则**：L1 ~ L2 在预发布或生产非核心流量时段进行；L3 ~ L5 只能在预发布 / GameDay 演练中进行。

## 从故障模式推导实验设计

### 常见的故障模式分类

混沌工程的价值不在于"随机制造故障"，而在于**从系统已知的脆弱性出发，有针对性地设计实验**。以下是常见的故障模式分类：

```
故障模式金字塔
         ▲
         │         应用级故障
         │    ┌──────────────────┐
         │    │ 依赖超时/OOM/GC  │
         │    │ 数据一致性/降级  │
         │    │ 限流失效/熔断    │
         │    └──────────────────┘
         │
         │         平台级故障
         │    ┌──────────────────┐
         │    │ K8s 组件异常     │
         │    │ Service Mesh 故障│
         │    │ DNS/服务发现     │
         │    │ 证书过期         │
         │    └──────────────────┘
         │
         │       基础设施级故障
  基础   │    ┌──────────────────┐
  频率   │    │ 网络延迟/丢包    │
         │    │ 磁盘 I/O 异常    │
         │    │ CPU/内存压力     │
         │    │ 实例/节点宕机    │
         │    └──────────────────┘
         └──────────────────────────
              修复复杂度 →
```

| 故障层级 | 故障类型 | 模拟方法 | 可能引发的系统行为 |
|---------|---------|---------|-----------------|
| **基础设施级** | 网络延迟 | Chaos Mesh network-delay | 超时→重试→连接池耗尽→雪崩 |
| | 网络丢包 | Chaos Mesh network-loss | TCP 重传→延迟增加→客户端超时 |
| | 磁盘 I/O异常 | Chaos Mesh io-fault | 写入延迟→队列堆积→OOM |
| | CPU 压力 | Chaos Mesh cpu-stress | 响应变慢→健康检查失败→Pod重启 |
| | 节点宕机 | AWS EC2 Stop / Node Kill | Pod 重新调度→数据丢失风险 |
| **平台级** | K8s API Server 不可用 | 模拟 API Server 故障 | 控制器无法调谐→状态不一致 |
| | DNS 解析失败 | Chaos Mesh dns-error | 服务发现失败→连接错误 |
| | Service Mesh 注入 | mTLS 证书过期 | TLS 握手失败→服务间通信中断 |
| | Ingress 不可达 | 删除 Ingress Controller Pod | 外部流量无法进入 |
| **应用级** | 依赖超时 | 人为增加依赖服务延迟 | 请求排队→线程池耗尽→级联故障 |
| | OOM | memory-stress 注入 | Pod OOMKill→重启→影响全部实例 |
| | 慢 SQL | 模拟数据库性能退化 | API 响应变慢→客户端超时→重试风暴 |
| | 降级失败 | 关闭降级开关 | 核心功能不可用 |

### 如何从历史故障推导实验优先级

```
实验优先级评估矩阵：

评分 = 故障频率 × 影响严重度 × 修复复杂度

故障频率：
  1 = 从未发生但有可能
  2 = 过去 2 年发生过
  3 = 过去 1 年发生过多次
  4 = 每季度都会遇到
  5 = 每月都会遇到

影响严重度：
  1 = 局部功能降级，不影响核心业务
  2 = 核心功能延迟增加，用户可感知
  3 = 核心功能部分不可用，影响 <1% 用户
  4 = 核心功能大面积不可用，影响 >5% 用户
  5 = 全站不可用（P0 事故）

修复复杂度：
  1 = 有成熟预案，5 分钟内可恢复
  2 = 有预案但需手动执行
  3 = 有降级方案但影响较大
  4 = 没有现成的方案，需临时排查
  5 = 无法快速恢复，依赖外部团队
```

**历史故障转化为实验清单的示例**：

```yaml
# 实验优先级排序
experiments:
  - name: payment-timeout-failover
    source_incident: "2024-03-15: 支付网关超时导致订单创建失败"
    fault_frequency: 3
    impact_severity: 5
    recovery_complexity: 2
    priority_score: 30  # 3×5×2 = 30（最高优先级）
    experiment: "注入 5s 延迟到支付服务，验证降级到备用支付通道"

  - name: redis-cluster-failover
    source_incident: "2024-01-20: Redis 主节点宕机导致会话数据丢失"
    fault_frequency: 2
    impact_severity: 4
    recovery_complexity: 3
    priority_score: 24  # 2×4×3 = 24
    experiment: "杀死 Redis 主节点，验证哨兵自动切换 + 会话重建"

  - name: db-connection-pool-exhaust
    source_incident: "2023-11-05: 慢查询导致连接池阻塞，DB 连接耗尽"
    fault_frequency: 4
    impact_severity: 3
    recovery_complexity: 1
    priority_score: 12  # 4×3×1 = 12
    experiment: "注入慢查询，验证连接池隔离和降级机制"
```

### 故障注入方法对比

| 注入方法 | 工作原理 | 性能开销 | 隔离性 | 适用场景 | 工具代表 |
|---------|---------|---------|-------|---------|---------|
| **Sidecar 注入** | 在 Pod 内注入 Sidecar 容器，劫持网络流量 | 低（网络层代理） | 好（每个 Pod 独立） | 网络故障注入（延迟、丢包） | Chaos Mesh (HTTPChaos) |
| **Agent 注入** | 在节点上运行 Agent，通过 cgroup/namespace 操作 | 中（占用节点资源） | 中（节点级共享） | CPU/内存/Disk 压力 | ChaosBlade |
| **eBPF 注入** | 内核态动态注入，无需修改应用代码 | 极低（内核级，无上下文切换） | 极好（精确到系统调用） | 网络故障、文件 I/O、系统调用错误 | Chaos Mesh (eBPF) |
| **K8s API 注入** | 通过 K8s API 操作资源（删除 Pod、更改配置） | 极低（仅为 API 调用） | 好（受 K8s 限制） | Pod 删除、配置变更 | kubectl / Litmus |

**性能与隔离性权衡**：

```
               隔离性
               高 ▲
                  │
        eBPF注入  │  Sidecar注入
        (极低开销)  │  (低开销)
                  │
                  │    Agent注入
                  │    (中等开销)
                  │
                  │     K8s API注入
                  │     (虚拟化级)
                  └─────────────────→ 性能开销
                  低                  高
```

> **推荐**：优先使用 eBPF（用于网络和 I/O 故障）和 Sidecar（用于应用层故障），避免 Agent 注入导致的节点级干扰。eBPF 是混沌工程未来的主流注入方式，因为它无需修改应用、性能开销极低、安全边界清晰。

## 混沌工程工具链

### Chaos Mesh（K8s 原生）

CNCF 项目，在 K8s 上注入各种故障。

![Chaos Mesh 架构示意](https://chaos-mesh.org/images/chaos-mesh-architecture.png)

```yaml
# Chaos Mesh Pod-Kill 实验
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: order-service-pod-kill
spec:
  action: pod-kill
  mode: one            # 随机选一个
  selector:
    namespaces:
      - prod
    labelSelectors:
      app: order-service
  duration: "60s"
  scheduler:
    cron: "@every 10m"  # 每 10 分钟执行一次
```

**Chaos Mesh 支持的故障类型**：

| 故障类型 | 模拟场景 | 控制参数 |
|---------|---------|---------|
| pod-kill | 容器重启/崩溃 | 数量、频率 |
| pod-failure | Pod 永久不可用 | 数量、持续时间 |
| network-delay | 网络延迟 | 延迟值、抖动 |
| network-loss | 网络丢包 | 丢包率 |
| network-partition | 网络分区 | 目标组 |
| cpu-stress | CPU 压力 | 核心数、负载率 |
| memory-stress | 内存压力 | 内存量 |
| io-fault | 磁盘 I/O 异常 | 延迟、错误率 |
| dns-error | DNS 解析失败 | 域名列表 |

## 弹性测试的自动化集成

### 混沌实验作为 CI/CD 流水线中的一站

将混沌工程嵌入 CI/CD 流水线，可以实现"每次部署都经过弹性验证"的韧性保障。

```
流水线阶段：
代码提交 → 单元测试 → 集成测试 → 弹性测试(混沌) → 安全扫描 → 部署上线
                                      │
                                      ├─ 注入故障（L1~L2 级别）
                                      ├─ 验证稳态假设
                                      └─ 通过/失败判定
```

```yaml
# GitLab CI 集成混沌实验
stages:
  - build
  - test
  - chaos-test     # 弹性测试阶段
  - security
  - deploy

chaos-test:
  stage: chaos-test
  image: instrumenta/chaos-mesh:latest
  script:
# 部署当前待发布版本到测试集群
    - kubectl apply -f k8s/overlays/test

# 等待所有 Pod 就绪
    - kubectl wait --for=condition=Ready pods --all -n test --timeout=120s

# 注入基准流量
    - ghz --insecure --proto ./api.proto --call api.OrderService.CreateOrder \
          --duration 60s --concurrency 10 \
          localhost:8080 &

# 执行混沌实验：网络延迟注入
    - kubectl apply -f chaos/network-delay-test.yaml

# 监控稳态指标（5 分钟窗口）
    - sleep 300

# 查询 Prometheus 验证稳态
    - |
      ERROR_RATE=$(curl -s "http://prometheus:9090/api/v1/query" \
        --data-urlencode 'query=rate(http_requests_total{status=~"5.."}[5m])' \
        | jq '.data.result[0].value[1] | tonumber')

      if (( $(echo "$ERROR_RATE > 0.01" | bc -l) )); then
        echo "❌ 弹性测试失败：错误率 $ERROR_RATE 超过阈值 0.01"
        exit 1
      fi
      echo "✅ 弹性测试通过：错误率 $ERROR_RATE < 0.01"
```

### 实验通过/失败的标准

混沌实验的通过标准不是"没有报错"，而是**稳态指标没有违反**。

```yaml
# 弹性测试通过/失败判定标准
pass_criteria:
  # 必须同时满足以下所有条件
  - metric: http_errors.rate
    operator: "<"
    threshold: 0.01         # 错误率 < 1%
    query: "rate(http_requests_total{status=~'5..'}[5m])"

  - metric: p99_latency
    operator: "<"
    threshold: "1000ms"     # P99 延迟 < 1000ms
    query: "histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))"

  - metric: business_success_rate
    operator: ">"
    threshold: 0.995        # 业务成功率 > 99.5%
    query: "rate(order_created_total[5m]) / rate(order_request_total[5m])"

  - metric: pod_restarts
    operator: "<"
    threshold: 3            # 实验期间 Pod 重启次数 < 3
    query: "sum(kube_pod_container_status_restarts_total{namespace='prod'})"

fail_criteria:
  # 出现以下任一条件则自动中断实验
  - metric: error_rate_spike
    operator: ">"
    threshold: 0.05         # 错误率 > 5% 立即中断
    query: "..."
    auto_stop: true         # 触发自动停止

  - metric: latency_breach
    operator: ">"
    threshold: "5000ms"     # 延迟 > 5s 立即中断
    query: "..."
    auto_stop: true
```

### 自动化回滚机制

混沌实验可能触发意想不到的连锁故障，因此必须配备自动化回滚能力。

```yaml
# 自动回滚机制设计
auto_remediation:
  # 熔断保护：实验触发后自动启用熔断
  circuit_breaker:
    triggers:
      - metric: error_rate
        threshold: 0.05
        action: "立即停止当前实验"
      - metric: cascade_detected
        threshold: true
        action: "触发全局熔断，暂停所有 Chaos 实验 30 分钟"

  # 实验恢复策略
  recovery:
# 自动停止 Chaos Experiment（删除 CRD）
    stop_experiment: |
      kubectl delete chaos $KIND $NAME -n $NAMESPACE

# 恢复受影响的资源
    restore_resources: |
      kubectl rollout undo deployment/$DEPLOYMENT -n $NAMESPACE
      kubectl scale deployment/$DEPLOYMENT --replicas=$ORIGINAL_REPLICAS

# 恢复网络配置
    restore_network: |
      kubectl delete networkchaos $NAME -n $NAMESPACE

# 通知告警
    notify: |
      curl -X POST "https://hooks.slack.com/services/..." \
        -H "Content-Type: application/json" \
        -d '{"text": "⚠️ 混沌实验自动回滚触发: '$NAME', 原因: '$REASON'"}'
```

**K8s 原生自动回滚实现**：

```yaml
# 使用 Chaos Mesh 的 Graceful Period 设置自动回滚
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: auto-rollback-demo
spec:
  action: delay
  mode: all
  selector:
    namespaces: [prod]
    labelSelectors:
      app: order-service
  delay:
    latency: "3000ms"
  duration: "120s"                 # 120 秒后自动停止
  gracefulPeriod: "30s"            # 30 秒优雅退出时间
  # ☠️ 安全机制：P95 延迟 > 5s 时自动停止
  toleration:
    - effect: NoSchedule
      key: chaos-experiment
  # 实验后自动恢复
  recovery:
    action: delete-target
    duration: "10s"
```

## 高可用架构模式

混沌工程发现系统的脆弱性，而以下架构模式是解决这些脆弱性的**设计范式**。

### 模式 1：冗余与多副本

```
┌──────────┐
│  LB      ├──→ Pod A (az-1)
│          ├──→ Pod B (az-2)
│          ├──→ Pod C (az-3)
└──────────┘
```

**目标**：避免单点故障

| 层级 | 冗余策略 |
|------|---------|
| 应用层 | 多副本 Deployment，跨可用区部署 |
| 数据层 | 主从复制、多副本、跨区容灾 |
| 网络层 | 多接入点、BGP Anycast |
| 物理层 | 多可用区、多数据中心 |

### 模式 2：断路器

> 见第 9 章 9.3.2——下游故障时自动熔断，防止级联雪崩。

### 模式 3：舱壁（Bulkhead）

**思想**：将系统隔离成独立舱室，一个舱室泄漏不影响其他。

```yaml
# 资源隔离示例：为不同服务分配独立的线程池和连接池
resilience4j:
  thread-pool-bouncer:
    instances:
      critical-service:
        max-thread-pool-size: 20
        core-thread-pool-size: 10
        queue-capacity: 100
      non-critical-service:
        max-thread-pool-size: 5
        core-thread-pool-size: 2
        queue-capacity: 20
```

### 模式 4：重试 + 退避

> 见第 9 章 9.3.4——临时性故障指数退避重试。

### 模式 5：超时控制

**最容易被忽视但最重要的模式之一**。

```go
// 每一层都要设置超时
ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
defer cancel()

// 数据库查询超时
queryCtx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
defer cancel()
db.QueryContext(queryCtx, "SELECT ...")
```

**超时传递原则**：外层超时 < 内层超时总和，预留缓冲。

### 模式 6：限流与降级

> 见第 9 章 9.3.1 和 9.3.3——保护系统不被流量洪峰击垮。

## 架构决策记录（ADR）在弹性设计中的应用

架构决策记录（Architecture Decision Record, ADR）是记录弹性设计决策的最佳实践。它帮助团队在混沌工程实验后追溯"为什么做这个决定"。

### ADR 模板

```markdown
# ADR-001：支付服务熔断策略

## 上下文
- 2024-03-15 P0 事故：支付网关超时导致级联故障，50% 用户受影响
- 支付服务依赖外部支付网关（Ping++），其 P99 延迟正常为 200ms，异常时可达到 10s+
- 当前无熔断保护，所有请求都等待超时，导致连接池耗尽

## 决策
在支付服务接入 resilience4j 断路器，采用以下配置：
- 滑动窗口：10 次请求
- 失败阈值：50%（5 次中 3 次失败即熔断）
- 熔断持续时间：30 秒
- 半开放状态：允许 3 次探测请求

## 后果
正面：
- 支付网关故障时，断路器在 30 秒内自动熔断，保护后续请求
- 熔断后降级为"支付失败请稍后重试"提示，而非一直挂起
- P99 延迟从 5s+ 降低到 500ms 以内

负面：
- 熔断期间所有支付请求直接失败，可能导致少量订单流失
- 需要协调前端做降级提示
- 误熔断风险：偶发抖动可能触发熔断

## 备选方案
1. **重试+指数退避**：不熔断，反复重试
   - 评估：连接池可能被长时间占用，不适合高并发场景
   - 结论：❌ 不采纳

2. **主动降级**：检测到延迟升高时自动切换到备用支付通道
   - 评估：需要维护备用通道，且涉及资金渠道切换风险
   - 结论：作为下阶段改进（已创建 EPIC-2024-042）

## 验证
- 混沌实验目标：注入 5s 延迟到支付服务，验证断路器在 30s 内熔断
- 实验状态：✅ 已通过（P95 延迟从 3s 降至 500ms）
```

### ADR 在弹性设计中的使用流程

```
混沌工程发现脆弱性
      ↓
创建 ADR：记录脆弱性、分析方案、做决策
      ↓
实施弹性改进（熔断/降级/限流）
      ↓
混沌工程验证：新实验验证改进效果
      ↓
ADR 状态更新：已实施 → 已验证 → 关闭
      ↓
下一次迭代：发现新脆弱性 → 新 ADR
```

**ADR 管理建议**：

| 实践 | 说明 |
|------|------|
| **ADR 存放位置** | 和代码一起存放在 Git 仓库的 `docs/adr/` 目录下 |
| **ADR 编号** | ADR-001, ADR-002... 递增，永不修改已有 ADR |
| **ADR 状态** | 提议中 → 已采纳 → 已实施 → 已验证 → 已废弃 |
| **关联混沌实验** | 每个 ADR 绑定一个或多个混沌实验作为验证依据 |
| **定期 Review** | 每季度 Review 所有 ADR，废弃不再适用的决定 |

## GameDay 演练

### 什么是 GameDay

> GameDay 是**有计划、有脚本的灾难演练**：某个时间段内，团队模拟一个重大故障场景，验证组织的应急响应能力。

### GameDay 流程

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ 场景设计  │→ │ 准备工作  │→ │ 执行演练  │→ │ 复盘改进 │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
```

### 常见 GameDay 场景

| 场景 | 模拟 | 验证目标 |
|------|------|---------|
| **AZ 宕机** | 关闭一个可用区的所有实例 | 跨可用区容灾 |
| **数据库主库挂掉** | 断开主库网络 | 主从切换 |
| **DNS 故障** | 清空 DNS 解析记录 | 降级/缓存机制 |
| **突发流量** | 10× 正常流量 | 自动扩缩容 + 限流 |
| **证书过期** | 删除/过期 TLS 证书 | 证书管理流程 |
| **第三方依赖挂掉** | 阻塞支付网关流量 | 降级+熔断 |

### GameDay 安全检查

```
□ 有明确的演练范围和影响边界
□ 演练时间非业务高峰期
□ 已通知相关干系人（含外部供应商）
□ 有紧急终止条件（Kill Switch）
□ 回滚方案已确认
□ 有独立的观察员记录全过程
□ 演练过程不修改真实用户数据
```

## 从混沌工程到韧性工程

混沌工程关注的是**验证系统已知的脆弱性**，而更高阶的韧性工程关注的是：

| 级别 | 关注点 | 实践 |
|------|--------|------|
| L1：反应式 | 出了问题能恢复 | 手动排障、事后复盘 |
| L2：主动式 | 自己能发现脆弱性 | 混沌工程、GameDay |
| L3：预防式 | 设计时就考虑故障 | 弹性架构设计模式 |
| L4：免疫式 | 系统自我修复 | 自愈、自动回滚、自适应限流 |

**组织的混沌工程成熟度**：

```
阶段1：好奇     —— 在测试环境手动跑混沌实验
阶段2：实验     —— 有实验设计和观察流程，定期跑
阶段3：持续     —— CI/CD 中嵌入自动化混沌实验
阶段4：常态     —— 生产环境中常态化运行，有全面的稳态度量和自动回滚
阶段5：免疫     —— 平台自动检测异常、自动注入故障验证、自动修复
```

## 生产案例：Netflix Chaos Monkey 实践

Netflix 是混沌工程的**发源地**，其 Chaos Monkey 的实践历程贯穿了混沌工程的整个发展史。

### 背景

Netflix，全球最大的流媒体平台，拥有 2.6 亿+ 付费用户，在全球 190+ 国家提供服务。其基础设施完全构建在 AWS 之上，依赖数千个 EC2 实例、数百个 RDS 数据库、数十个缓存集群。

### 核心痛点

| 痛点 | 详细说明 |
|------|---------|
| **AWS 实例可能随时故障** | EC2 实例会出现硬件故障、网络问题、宿主机异常，且 AWS 不会预先通知 |
| **系统复杂度不可预测** | 数百个微服务互相调用，没有人能完全预测故障下的行为 |
| **传统测试不够** | 单元测试和集成测试只能验证"一切正常"的情况 |
| **被动响应成本高** | 每次真实故障影响数百万用户的观看体验，代价巨大 |
| **混沌工程理念超前** | 2010 年，主动在生产环境制造故障被认为是疯狂的 |

### 演进历程

#### 2010：Chaos Monkey 诞生

> "如果某天 AWS 实例肯定会出问题，为什么不等它出问题，而是主动让它出问题？"

**Chaos Monkey 1.0 设计**：

```python
# Chaos Monkey 工作原理（伪代码）
class ChaosMonkey:
    def __init__(self):
        self.target_termination_rate = 0.01  # 每天终止 1% 的实例
        self.excluded_groups = ["prod-critical"]  # 例外群组

    def run_daily(self):
        for asg in self.get_all_auto_scaling_groups():
            if asg.name in self.excluded_groups:
                continue
            if random.random() < self.target_termination_rate:
                instance = random.choice(asg.instances)
                self.terminate_instance(instance)
                self.log("Terminated: {instance.id} from {asg.name}")

    def should_terminate(self, asg, instance):
        """运行时间内随机杀死，确保不可预测"""
        return (random.random() < 0.01
                and self.is_business_hours()  # 工作时间运行
                and asg.min_size < asg.desired_capacity)  # 保留最小容量
```

**关键设计决策**：

| 决策 | Netflix 的答案 | 理由 |
|------|---------------|------|
| 在生产环境还是测试环境运行？ | **生产环境** | 真实流量模式无法模拟 |
| 工作时间还是非工作时间？ | **工作时间** | 团队在岗时可以及时响应 |
| 通知团队还是秘密进行？ | **不提前通知** | 检验真实的应急响应能力 |
| 杀死多少实例？ | **每天 1%** | 足够低的概率，不引发大规模故障 |
| 自动终止条件？ | **保持 ASG 最小容量** | 确保不会杀死所有实例 |

#### 2012：Chaos Kong

模拟 AWS Region 级别的故障：

```yaml
# Chaos Kong 实验设计
chaos_kong:
  scenario: "模拟整个 AWS Region 不可用"
  target_region: "us-east-1"
  failover_region: "us-west-2"

  steps:
# 将 us-east-1 的 Route53 DNS 记录全部移除
# S3 跨 Region 复制验证
# 将所有流量切到 us-west-2
# 验证用户观看体验不受影响

  criteria:
    - "p99 启动时间增加 < 2s"
    - "无用户 session 丢失"
    - "新用户正确定位到 us-west-2"
    - "系统在 30 分钟内恢复全容量"
```

#### 2014：Simian Army — 多只猴子

```
Simian Army（猿军）：
├─ Chaos Monkey     — 随机杀死生产实例
├─ Latency Monkey   — 在服务间注入延迟
├─ Conformity Monkey — 检查实例是否偏离最佳实践配置
├─ Doctor Monkey    — 检测不健康实例并从负载均衡中移除
├─ Janitor Monkey   — 清理未使用的云资源（降低云成本）
├─ Security Monkey  — 检查安全漏洞和权限问题
├─ 10-18 Monkey     — 检测多区域/多语言配置问题
└─ Chaos Gorilla    — 模拟整个可用区故障
```

#### 2018+：自建混沌平台

Netflix 从开源的 Chaos Monkey 转向了自己内部管理的混沌平台，核心变化：

1. **从随机到定向**：不再是"随机杀死一个实例"，而是根据业务优先级和敏感性设计实验
2. **精细化控制**：Blast Radius（爆炸半径）可精确控制到特定服务、特定用户群
3. **自动回滚**：检测到异常指标时自动停止实验并恢复
4. **集成可观测性**：与 Atlas（Netflix 的监控系统）深度集成，实验前后自动对比指标
5. **实验即代码**：混沌实验作为代码定义，纳入 CI/CD 流水线

### Netflix 混沌工程的设计原则

```
┌─────────────────────────────────────────┐
│ Netflix Chaos Engineering 原则            │
├─────────────────────────────────────────┤
│ 1. 在生产环境（工作时间）运行             │
│    理由：只有生产环境有真实流量模式       │
│    条件：团队在岗，能及时响应异常        │
├─────────────────────────────────────────┤
│ 2. Blast Radius 可控                     │
│    最小化爆炸半径：L1 → L2 → L3 渐进     │
│    例外群组：永远不会影响核心支付/认证    │
├─────────────────────────────────────────┤
│ 3. 自动化执行 + 持续运行                 │
│    不是一次性活动，而是持续机制           │
│    Chaos Monkey 每天运行                 │
├─────────────────────────────────────────┤
│ 4. 假设被证实而不是被依赖                 │
│    混沌实验不是为了"测试通过"             │
│    而是为了"验证假设"或"发现盲点"        │
├─────────────────────────────────────────┤
│ 5. 从故障中学习，而不是修复故障           │
│    目标不只是让实验通过                   │
│    而是让系统变得更健壮                  │
└─────────────────────────────────────────┘
```

### 效果

| 指标 | Chaos Monkey 之前 | Chaos Monkey 之后 |
|------|-----------------|------------------|
| **AZ 宕机故障响应时间** | 30+ 分钟 | < 2 分钟（自动切换） |
| **Region 故障恢复** | 小时级 | 30 分钟内自动恢复 |
| **微服务容错能力** | 一个实例故障可能影响全站 | 任意单个 AZ 故障不影响用户 |
| **部署信心** | 每次部署紧张 | 有信心随时部署（即使 Chaos Monkey 运行中） |
| **故障发现** | 只有真实用户报错才能发现 | 主动+持续发现脆弱性 |
| **系统韧性文化** | 运维团队疲于救火 | 工程师在设计时就考虑故障 |

### Netflix 实践给我们的启示

```
├─ 不必一步到位
│  从 Chaos Monkey 开始（一个故障类型，最小风险）
│  再到 Simian Army（多种故障类型，逐步扩展）
│  最后是自建混沌平台（全面掌控）
├─ 生产环境是必要条件
│  测试环境永远无法复现真实流量
│  但从小开始：先做非核心服务，逐步扩大
├─ 重要的是文化，不是工具
│  工具可以现成拿（Chaos Mesh / Litmus）
│  但"接受故障是常态"的文化需要时间建立
├─ Blast Radius 第一
│  先定义"最坏情况"，再决定实验范围
│  始终保留 Kill Switch
└─ 混沌工程是持续过程，不是一次性项目
   Netflix 做了 10+ 年混沌工程，仍在持续改进
```

| 章节 | 主题 | 核心价值 |
|------|------|---------|
| 1 | DevOps 理念 | 理解"为什么"要 DevOps |
| 2 | Git 工作流 | 版本控制——一切自动化的基础 |
| 3 | CI | 自动化构建与测试——效率保障 |
| 4 | CD 与部署 | 安全、可靠的发布策略 |
| 5 | IaC | 用代码管理基础设施 |
| 6 | Docker | 容器化——环境一致性方案 |
| 7 | K8s | 容器编排——集群管理利器 |
| 8 | 可观测性 | 知道系统在发生什么 |
| 9 | 服务治理 | 微服务间的通信和控制 |
| 10 | DevSecOps | 安全左移，嵌入全流程 |
| 11 | GitOps | Git 为唯一真相源 |
| 12 | 混沌工程 | 主动破坏，发现盲点 |

软件工程没有银弹，但系统化的知识体系能帮你做出更好的决策。**持续学习、持续实践、持续改进**——这是 DevOps 文化的终极精神。
