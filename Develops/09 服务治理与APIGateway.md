# 第9章：服务治理与 API 网关

## 本章学习目标

- 理解微服务架构下的治理挑战
- 掌握 API 网关的核心职责与典型能力
- 了解限流、熔断、降级、重试等治理模式
- 了解服务网格（Service Mesh）与 Istio 的基本概念

## 微服务治理的挑战

### 从单体到微服务

```
单体应用                        微服务
┌──────────────┐           ┌────┐ ┌────┐ ┌────┐
│ 认证 订单 支付 │    →    │Auth│ │Ord │ │Pay │
│ 用户 商品 通知 │           └────┘ └────┘ └────┘
│              │           ┌────┐ ┌────┐ ┌────┐
│ 全部在同一个  │           │Usr │ │Prod│ │Noti│
│ JAR/WAR 进程 │           └────┘ └────┘ └────┘
└──────────────┘
```

### 微服务带来的新问题

| 问题 | 单体时期 | 微服务时期 |
|------|---------|-----------|
| 服务发现 | 本地调用 | 需知道其他服务 IP 和端口 |
| 负载均衡 | 单体内置 | 需在多个实例间分发请求 |
| 限流 | 全局限流 | 需要每个服务各自限流 + 全局限流 |
| 熔断 | 整个应用熔断 | 需要下游故障时优雅降级 |
| 重试 | 内部方法重试 | 需考虑幂等性和级联重试 |
| 安全 | 统一处理 | 每个服务需验证 Token |
| 超时 | 方法级超时 | 需设置精确的请求超时 |

## API 网关

### 网关位置

```
                  ┌──────────┐
外部请求 ───────→│  API     │──→ Auth Service
                  │  Gateway │──→ Order Service
                  └──────────┘──→ Payment Service
                      │          → User Service
                      │
                      ▼
                  ┌──────────┐
                  │  监控/日志 │
                  └──────────┘
```

### 网关的核心职责

| 能力 | 说明 | 典型实现 |
|------|------|---------|
| **统一入口** | 单一域名，内部路由 | 路径/Header 路由 |
| **认证授权** | 统一的身份验证 | JWT / OAuth2 验证 |
| **限流** | 防止流量洪峰 | 令牌桶 / 漏桶 |
| **负载均衡** | 后端实例分发 | Round-Robin / 一致性哈希 |
| **请求/响应转换** | 协议转换、格式转换 | HTTP → gRPC |
| **缓存** | 响应缓存 | 热点数据缓存 |
| **日志/监控** | 统一采集 | 请求出入日志 |
| **跨域** | CORS 处理 | 配置 Origin 白名单 |
| **断路器** | 检测下游故障 | 自动熔断 |

### 主流 API 网关对比

| 网关 | 语言 | 性能 | 扩展性 | 社区 |
|------|------|------|--------|------|
| **Kong** | Lua/Go | 高（基于 OpenResty）| 插件丰富 | CNCF |
| **APISIX** | Lua/Go | 极高 | 动态编排 | Apache |
| **Nginx Plus** | C | 高 | 模块 | 商业版 |
| **Envoy** | C++ | 极高 | L4/L7 代理 | CNCF（Istio 的 Data Plane）|
| **Spring Cloud Gateway** | Java | 中 | Spring 生态 | 广泛 |
| **Traefik** | Go | 高 | K8s 原生 | CNCF |

### API 网关 vs Service Mesh 边界划分

在大规模微服务架构中，API 网关和服务网格（Service Mesh）的能力存在重叠——两者都能做限流、认证、路由、重试。关键问题在于：**什么能力放在网关层，什么能力放在 Sidecar 层？**

**南北向 vs 东西向流量"二分法"**：

```
                          ┌──────────────────┐
 外部客户端 ──────────────→│   API Gateway    │ ← 南北向流量（North-South）
                          │  ─ 认证 / 限流    │
                          │  ─ 协议转换 / 路由 │
                          │  ─ WAF / 跨域     │
                          └────────┬─────────┘
                                   │
               ┌───────────────────┼───────────────────┐
               │                   │                   │
               ▼                   ▼                   ▼
          ┌────────┐         ┌────────┐          ┌────────┐
          │ Auth   │ ◄─────→ │ Order  │ ◄──────→ │Payment │
          │ Service│ ←──────→│ Service│ ←───────→│Service │
          └───┬────┘         └───┬────┘          └───┬────┘
              │ Envoy            │ Envoy             │ Envoy
              └──────────────────┴───────────────────┘
                ← 东西向流量（East-West）→
                Service Mesh (Istio) 负责：
                - 服务发现 / 负载均衡
                - 重试 / 熔断 / 超时
                - mTLS / 零信任安全
                - 链路追踪 / 统一指标
```

**能力归属矩阵**：

| 能力 | 应放在哪里 | 理由 |
|------|-----------|------|
| **外部认证**（OAuth2 / JWT 验证） | 网关层 | 一次验证，所有内部服务无需重复验证 Token；网关可直接拒绝非法请求 |
| **内部服务认证**（mTLS） | 网格层 (Sidecar) | 服务间通信使用 mTLS 无需经过网关，降低延迟 |
| **限流（外部）** | 网关层 | 外部突发流量在网关处拦截，保护整个后端集群 |
| **限流（内部）** | 网格层 (Sidecar) | 服务间调用的细粒度限流，如 B 服务限制 A 服务的调用频率 |
| **路由（外部→内部）** | 网关层 | 域名/路径 → 服务名的映射，协议转换（HTTP → gRPC）|
| **路由（内部→内部）** | 网格层 (Sidecar) | 金丝雀发布、流量分割、版本路由（v1 vs v2）|
| **熔断** | 网格层 (Sidecar) | 熔断应发生在每个调用方，而非网关统一管理；Sidecar 层熔断更精确 |
| **重试** | 网格层 (Sidecar) | 幂等重试应在调用方本地控制，网关重试可能导致跨服务级联问题 |
| **请求/响应转换** | 网关层 | 外部格式与内部格式的转换在入口做一次即可 |
| **负载均衡** | 网格层 (Sidecar) | Sidecar 感知后端实例健康状态，本地负载均衡更高效 |
| **WAF / DDoS 防护** | 网关层（外部专用 WAF） | 安全设备通常在网关前独立部署 |
| **链路追踪** | 两层都采集 | 网关生成外部请求的初始 Span，Sidecar 自动传播内部 Span |
| **访问日志** | 两层都采集 | 网关记录外部请求日志，Sidecar 记录服务间调用日志 |

**避免重复配置的关键原则**：

```
原则 1：外部入口 → 网关，内部路由 → 网格
原则 2：全局策略（认证、全局限流、协议转换）→ 网关
原则 3：局部策略（服务间熔断、重试、本地限流）→ 网格
原则 4：两者同时配置的能力 → 网关优先（外部请求先过网关）
```

**推荐方案对比：网关 + Sidecar 选型**：

| 组合方案 | 网关 | 网格控制面 | 复杂度 | 适用规模 |
|---------|------|-----------|--------|---------|
| **Kong + Istio** | Kong (OpenResty) | Istio (Envoy) | 中 | 200+ 服务，成熟的 K8s 平台 |
| **APISIX + Istio** | APISIX (高性能 Lua) | Istio (Envoy) | 中 | 大流量场景，需要极致网关性能 |
| **Envoy 作为网关 + Istio** | Envoy（Gateway API） | Istio | 高 | 统一 Envoy 技术栈，团队有 Envoy 专家 |
| **Traefik + Istio** | Traefik (K8s 原生) | Istio | 低 | 小规模 K8s 原生团队（50 服务以内）|
| **Kong + 无网格** | Kong | 无 | 低 | 50 服务以内，治理需求简单 |
| **Nginx + Kong 插件** | Nginx + Kong 插件 | 无 | 中 | 传统运维团队，不需要网格 |

**特殊场景：什么时候不需要 Service Mesh？**

```
├── 服务数 < 20 个
│   └── 治理需求在网关层配合客户端库即可解决
│       （如 resilience4j + Feign Client）
├── 团队运维能力不足
│   └── Istio 的 Sidecar 注入、升级、排错需要 K8s 专家
├── 延迟极其敏感（P99 < 10ms）
│   └── 每个 Sidecar 增加 2-5ms 延迟，在延迟敏感场景不可接受
├── 服务器资源紧张
│   └── 每个 Pod 多一个 Sidecar（~50MB 内存），500 个 Pod 额外消耗 25GB
└── 只有部分服务需要迁移
    └── 可以仅在需要治理的服务上启用 Sidecar，或使用 Istio 的 Selective Injection
```

## 核心治理模式

### 限流

**目标**：保护后端不被突发流量击垮。

| 算法 | 原理 | 特点 |
|------|------|------|
| **令牌桶** | 按固定速率放入令牌，每次请求取一个令牌 | 允许一定程度的突发流量 |
| **漏桶** | 请求以固定速率流出（处理），超出的丢弃或排队 | 严格平滑流量 |
| **滑动窗口** | 统计时间窗口内的请求数 | 避免固定窗口的"毛刺"问题 |
| **自适应限流** | 根据系统负载动态调整限流阈值 | 自动化，需准确度量 |

```yaml
# APISIX 限流配置示例
plugins:
  limit-req:
    rate: 100        # 每秒允许的请求数
    burst: 50        # 突发阈值
    nodelay: true    # 是否延迟处理超出的请求
    key: remote_addr # 基于 IP 限流
```

**限流粒度**：全局限流 → 路由级限流 → 用户级限流 → API 级限流

**限流算法选型决策树**：

```
第一步：流量特征
  ├── 需要容忍突发流量（如电商秒杀、活动抢购）
  │   └── → 令牌桶算法
  ├── 需要严格平滑流量（如支付回调、消息推送）
  │   └── → 漏桶算法
  ├── 需要防刷/防恶意请求（API 防滥用）
  │   └── → 滑动窗口（统计粒度高）
  └── 需要精确的速率控制（如 SMS 发送频率限制）
      └── → GCRA（通用细胞速率算法）

第二步：部署形态
  ├── 单机部署 / 单实例 → 本地限流（内存计算，零网络开销）
  │   └── 推荐：令牌桶（Guava RateLimiter / resilience4j）
  └── 分布式多实例 → 分布式限流（需中心化存储）
      ├── Redis + Lua 脚本（灵活，可控）
      │   └── 推荐：Redis 令牌桶 / Redis 滑动窗口
      └── Sentinel（阿里开源，控制台管理）
          └── 推荐：Java 生态，有可视化控制台

第三步：限流维度
  ├── IP 地址 → 防 DDoS / 防爬虫（效果最直接）
  ├── UserID → 防止单个用户滥用（业务精确）
  ├── API Key → 第三方 API 调用量控制（B 端 API 网关场景）
  └── 全局 → 保护后端集群整体容量（兜底线）
```

**算法特性对比矩阵**：

| 维度 | 令牌桶 | 漏桶 | 滑动窗口 | GCRA |
|------|--------|------|---------|------|
| **允许突发** | ✅ 是（burst 参数控制）| ❌ 否（严格平滑）| ❌ 否 | ⚠️ 有限度 |
| **平滑流量** | ⚠️ 中等 | ✅ 极好 | ✅ 好 | ✅ 好 |
| **实现复杂度** | 低 | 低 | 中 | 中-高 |
| **内存开销** | 低（1 个计数） | 低（队列） | 中（窗口内记录） | 低（1 个时间戳） |
| **分布式支持** | 需 Redis | 需 Redis | 需 Redis | 好（原生支持） |
| **精确度** | 中（允许瞬间突发） | 高 | 高 | 极高 |
| **典型使用** | API 网关大部分场景 | 消息队列消费速率 | 防刷 / 防爬虫 | CDN / 电信领域 |

**分布式限流：Redis + Lua 实现令牌桶**：

```lua
-- Redis Lua 脚本：分布式令牌桶限流
-- KEYS[1] = 限流 key（如 "rate_limit:user:u-1001"）
-- ARGV[1] = 速率（每秒令牌数）
-- ARGV[2] = 桶容量
-- ARGV[3] = 当前时间戳（毫秒）
local key = KEYS[1]
local rate = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 获取当前桶状态
local bucket = redis.call("hmget", key, "tokens", "last_refill")
local tokens = tonumber(bucket[1] or capacity)
local last_refill = tonumber(bucket[2] or now)

-- 计算应补充的令牌数
local elapsed = math.max(0, now - last_refill)
local refill = elapsed * rate / 1000
tokens = math.min(capacity, tokens + refill)

-- 消费一个令牌
if tokens >= 1 then
    tokens = tokens - 1
    redis.call("hmset", key, "tokens", tokens, "last_refill", now)
    redis.call("expire", key, math.ceil(capacity / rate) * 2)
    return 1  -- 允许请求
else
    return 0  -- 限流拒绝
end
```

**限流后的反馈：HTTP 429 最佳实践**：

```text
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 120
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1717924800

{
  "error": {
    "code": "RATE_LIMITED",
    "message": "请求过于频繁，请在 120 秒后重试",
    "retry_after_seconds": 120
  }
}
```

| Header | 说明 | 必要性 |
|--------|------|--------|
| **Retry-After** | 建议客户端等待的秒数（整数） | ✅ 必须 |
| **X-RateLimit-Limit** | 时间窗口内的限额 | 推荐 |
| **X-RateLimit-Remaining** | 当前窗口剩余额度 | 推荐 |
| **X-RateLimit-Reset** | 额度重置的 Unix 时间戳 | 推荐 |
| 响应体含错误码 + 重试时间 | 客户端可以据此做智能重试 | ✅ 最佳实践 |

**限流降级策略**：

| 策略 | 客户端表现 | 适用场景 |
|------|-----------|---------|
| **快速失败** | 直接返回 HTTP 429，客户端自行处理 | 大多数 API 场景 |
| **排队等待** | 请求进入队列，按速率处理 | 消息推送、回调 |
| **降级响应** | 限流时返回兜底数据（如缓存的最新数据）| 读多写少的查询类 API |
| **熔断隐式限流** | 限流与熔断联动，超阈值后直接断开 | 关键路径保护 |

### 熔断

**目标**：当下游服务故障时，快速失败的调用方不应继续等待或加重下游负担。

**状态机**：

```
              ┌──────────┐
         ┌──→│  CLOSED  │ ←── 正常调用
         │   │ (关闭)    │
         │   └────┬─────┘
         │        │ 失败率 > 阈值
         │        ▼
         │   ┌──────────┐
         │   │  OPEN    │ ──→ 直接拒绝请求，快速失败
         │   │ (打开)    │
         │   └────┬─────┘
         │        │ 超时窗口结束
         │        ▼
         │   ┌──────────┐
         │   │ HALF-OPEN│ ──→ 尝试放行少量请求
         │   │ (半开)   │
         │   └────┬─────┘
         │        │
         └────────┘ 成功 → 重置为 CLOSED
                     失败 → 回到 OPEN
```

```yaml
# 熔断配置示例
resilience4j.circuitbreaker:
  instances:
    order-service:
      sliding-window-size: 10       # 统计窗口大小（10 次请求）
      failure-rate-threshold: 50    # 50% 失败率触发熔断
      wait-duration-in-open-state: 30s  # 半开前等待 30 秒
      permitted-number-of-calls-in-half-open-state: 3  # 半开状态允许的请求数
```

**熔断器参数调优指南**：

熔断器配置高度依赖业务场景，错误配置会导致两种问题：**过早熔断（假阳性）** 或 **熔断不及时（假阴性）**。

**滑动窗口大小选型**：

```
根据请求量级选择滑动窗口大小（滑动窗口 = 统计历史请求的缓冲区大小）：

| 场景 | 每秒调用量 | 推荐窗口大小 | 理由 |
|------|-----------|-------------|------|
| 高流量 API（订单、支付） | > 1000 QPS | 100 次请求 | 窗口小但时间短，10 秒内出结论 |
| 中等流量 API（用户查询） | 100-1000 QPS | 50 次请求 | 平衡灵敏度与稳定性 |
| 低流量 API（报表导出） | < 10 QPS | 10 次请求或时间窗口 60s | 统计周期长，防止偶然波动误判 |
| 定时任务 / 批处理 | 低并发，突发 | 基于时间窗口 120s | 请求数量少，不适合基于次数的统计 |

核心原则：
  高流量 → 基于次数（sliding-window-size）
  低流量 → 基于时间（sliding-window-minimum-number + 时间窗口）

建议：
  ├── QPS > 100: 次数窗口 100
  ├── QPS > 10: 次数窗口 50
  └── QPS < 10: 时间窗口 60s + 最小请求数 5
```

**熔断恢复策略**：

| 恢复策略 | 原理 | 优势 | 劣势 | 适用场景 |
|---------|------|------|------|---------|
| **全量恢复** | 半开状态通过后，直接恢复为 CLOSED（全量请求）| 恢复速度快 | 如果下游仍有问题，可能再次击溃 | 重试成本低的非关键服务 |
| **渐进式恢复** | 半开状态逐步增加放行比例（如 10% → 30% → 100%）| 稳定，逐步验证下游健康 | 恢复期长 | 关键链路服务（支付、订单）|
| **保守恢复** | 半开 → CLOSED 后，增加一个"冷启动"窗口，限制初期并发 | 最安全 | 用户体验恢复慢 | 出现过雪崩的服务 |

```yaml
# 渐进式恢复 (Resilience4j 无原生支持，需自定义或使用 Istio)
# Istio 熔断配置（支持渐进恢复）
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: order-service-cb
spec:
  host: order-service
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
    outlierDetection:
      consecutive5xxErrors: 5       # 连续 5 次 5xx 触发熔断
      interval: 30s                   # 每 30s 检测一次
      baseEjectionTime: 30s           # 最小驱逐时间 30s
      maxEjectionPercent: 50          # 最多驱逐 50% 的实例
      # Istio 的熔断是实例级别的驱逐，驱逐时间会随次数指数增长
      # 第一次驱逐: 30s
      # 第二次驱逐: 60s (翻倍)
      # 第三次驱逐: 120s
      # 这实际上实现了渐进式恢复
```

**与重试的交互：熔断打开时不应重试**：

```
❌ 错误做法：重试逻辑不感知熔断状态

客户端                     下游服务
  │                          │
  ├── Request ──────────────→│ 服务负载高，响应慢
  ├── Retry (1s) ──────────→│ 还是慢
  ├── Retry (2s) ──────────→│ 雪上加霜
  ├── Retry (4s) ──────────→│ 崩溃！
  │                          │

✅ 正确做法：熔断 + 重试联动

客户端                     下游服务
  │                          │
  ├── Request ──────────────→│ 响应超时 5s
  ├── Retry (1s) ──────────→│ 再次超时
  │  (失败率触发熔断阈值)    │
  │  【熔断器 OPEN】         │
  ├── 重试被熔断拦截         │  ── 下游服务有机会恢复
  ├── 重试被熔断拦截         │
  │  【等待半开超时】        │
  ├── Half-Open Request ───→│ 恢复正常
  │  【熔断器 CLOSED】      │
  └── Request ─────────────→│ 正常响应
```

**代码示例：熔断 + 重试联动**：

```java
// Resilience4j 熔断 + 重试组合
CircuitBreaker circuitBreaker = CircuitBreakerRegistry.ofDefaults()
    .circuitBreaker("order-service", circuitBreakerConfig);

Retry retry = RetryRegistry.ofDefaults()
    .retry("order-service-retry", retryConfig);

// 关键：重试装饰器感知熔断状态
// 熔断打开时，重试装饰器不会执行重试逻辑
// 而是直接抛出 CircuitBreakerOpenException
CheckedRunnable decorated = CircuitBreaker.decorateCheckedRunnable(
    circuitBreaker,
    Retry.decorateCheckedRunnable(retry, () -> orderClient.pay(orderId))
);

try {
    decorated.run();
} catch (CircuitBreakerOpenException e) {
    // 熔断打开，不重试，直接返回降级响应
    return fallbackResponse("订单服务暂时不可用，请稍后重试");
} catch (Exception e) {
    // 其他异常
    log.error("调用订单服务失败", e);
    return fallbackResponse("系统异常，请联系客服");
}
```

**实际生产参数配置对照表（基于经验值）**：

| 服务类型 | 示例 | 滑动窗口 | 失败阈值 | 半开等待 | 半开请求数 | 说明 |
|---------|------|---------|---------|---------|-----------|------|
| **关键支付链路** | payment-svc | 基于时间 60s + 最少 20 次 | 30% | 60s | 5 | 保守设置，防止误熔断 |
| **高流量查询** | user-svc | 次数 100 次 | 50% | 30s | 5 | 容忍更高容错率 |
| **外部依赖** | sms-provider | 次数 50 次 | 40% | 120s | 3 | 外部服务恢复慢，等待时间长 |
| **基础设施** | redis-cache | 次数 20 次 | 60% | 15s | 5 | 快速熔断，快速恢复 |
| **批处理服务** | report-gen | 时间 120s + 最少 5 次 | 50% | 90s | 2 | 低频率，长周期统计 |

### 降级

**目标**：当部分功能不可用时，提供**有限但可接受**的服务体验。

| 降级类型 | 示例 | 用户感知 |
|---------|------|---------|
| **返回兜底数据** | 推荐服务不可用 → 返回热门推荐 | 有限但可用 |
| **降级为静态页** | 个性化页面不可用 → 展示通用页面 | 功能降级 |
| **关闭非核心功能** | 评论区不可用 → 隐藏评论区 | 核心功能正常 |
| **降级为异步处理** | 发送通知 → 落入队列，延后处理 | 延迟但最终一致 |

### 重试

**目标**：对临时性故障（如网络抖动）进行自动重试。

**注意**（否则重试会变成灾难）：

```
客户端重试 → 上游服务承受更大压力 → 进一步恶化 → 更多重试 → 雪崩
```

**重试最佳实践**：
1. **幂等性**：只有幂等的 API 才允许重试
2. **退避策略**：使用指数退避（Exponential Backoff） + 抖动（Jitter）
3. **最大重试次数**：通常 ≤ 3 次
4. **与熔断配合**：熔断开启后不再重试

```java
// 指数退避重试示例
int maxRetries = 3;
long baseDelay = 100; // ms
for (int i = 0; i < maxRetries; i++) {
    try {
        return callService();
    } catch (TransientException e) {
        long delay = baseDelay * (long) Math.pow(2, i) + ThreadLocalRandom.current().nextLong(0, 100);
        Thread.sleep(delay);
    }
}
```

## 服务网格（Service Mesh）

### 为什么需要 Service Mesh

K8s 时代，应用的流量管理需求越来越复杂：

```
Sidecar 模式：
┌─────────────────────┐
│       Pod           │
│  ┌──────────────┐   │  ← 应用容器（业务代码）
│  │   App        │   │
│  └──────┬───────┘   │
│         │ localhost │
│  ┌──────▼───────┐   │  ← Sidecar 代理（Envoy）
│  │   Proxy      │   │
│  │  (Envoy)     │   │
│  └──────────────┘   │
└─────────────────────┘
```

**Service Mesh 将微服务通信的通用能力从业务代码中剥离到代理层**：限流、熔断、负载均衡、服务发现、TLS、追踪等，业务代码不再需要关心这些。

### Istio 架构

```
┌─────────────────────────────────────┐
│            Istio Control Plane      │
│  ┌─────────┐ ┌─────────┐ ┌───────┐ │
│  │ Pilot   │ │ Citadel │ │Galley │ │
│  │ (流量)  │ │ (安全)  │ │(配置) │ │
│  └────┬────┘ └────┬────┘ └───────┘ │
└───────┼───────────┼─────────────────┘
        │           │
    ┌───┴───────────┴───┐
    │    K8s API        │
    └───────────────────┘
              │
┌─────────────┼─────────────────────────┐
│      Data Plane（所有 Pod）            │
│  ┌─────┐  ┌─────┐  ┌─────┐           │
│  │Envoy│  │Envoy│  │Envoy│           │
│  └──┬──┘  └──┬──┘  └──┬──┘           │
│     │        │        │               │
│   App A    App B    App C            │
└─────────────────────────────────────┘
```

| 能力 | 说明 |
|------|------|
| **流量管理** | 金丝雀发布、流量分割、超时、重试、熔断 |
| **安全** | mTLS（双向 TLS）、RBAC、认证策略 |
| **可观测性** | 自动采集指标、链路追踪、访问日志 |
| **多集群** | 跨 K8s 集群的服务网格 |

### 服务网格的代价

Service Mesh 解决了诸多治理问题，但也带来了不可忽视的成本。决策者需要在"引入网格"和"维持现状"之间做量化权衡。

**资源开销：每个 Pod 增加一个 Sidecar 代理**

```
┌──────────────────────────┐
│  Pod 资源分配            │
│                          │
│  App Container           │
│  ├── CPU: 1 core         │
│  └── Memory: 512Mi       │
│                          │
│  Envoy Sidecar           │
│  ├── CPU: 0.25 core      │
│  └── Memory: 64Mi        │  ← 附加 12.5% 的资源开销
│                          │
│  总计: CPU +25%          │
│        Memory +12.5%     │
└──────────────────────────┘
```

**资源开销实测数据（基于 Istio 1.20 + Envoy 1.28 生产部署）**：

| 场景 | Sidecar CPU | Sidecar 内存 | 总资源增加 |
|------|------------|-------------|-----------|
| **低流量服务**（< 100 QPS） | 0.1-0.2 core | 40-60 MB | +10%-15% |
| **中等流量服务**（100-1000 QPS） | 0.2-0.5 core | 60-80 MB | +15%-25% |
| **高流量服务**（> 1000 QPS） | 0.5-1.0 core | 80-150 MB | +25%-40% |
| **代理密集配置**（大量 Policy/Rule） | +0.3 core | +20-40 MB | 额外叠加 |

**一个 500 Pod 集群的 Sidecar 附加成本估算**：

```text
基准：500 Pod × 每 Pod 附加 50MB 内存 + 0.25 core CPU
内存：500 × 50MB = 25GB 额外内存
CPU：500 × 0.25 = 125 额外 CPU 核
按 AWS 价格估算：
  内存：25GB × $0.01/GB/h × 730h = $182.5/月
  CPU：125核 × $0.03/核/h × 730h = $2,737.5/月
         ────────
  总计约 $2,920/月（约 ¥21,000/月）
```

**延迟增加**：

```
客户端 → [Envoy Sidecar] → 服务 A → [Envoy Sidecar] → 服务 B

一次服务间调用的路径：
  客户端 → Sidecar_A (localhost) → 服务 A → Sidecar_A → Sidecar_B → 服务 B

延迟分解（P99 对比）：
┌────────────────────────────────────────────┐
│ 无 Sidecar: 客户端 → 服务A → 服务B         │
│ 延迟: 5ms + 10ms = 15ms                    │
├────────────────────────────────────────────┤
│ 有 Sidecar (Istio):                        │
│ 客户端 → Envoy_A → 服务A → Envoy_A         │
│        → Envoy_B → 服务B                   │
│ 延迟: 2ms + 5ms + 2ms + 2ms + 10ms = 21ms │
│ 附加延迟: 6ms (+40%)                       │
├────────────────────────────────────────────┤
│ 实际生产建议: 预期 P99 增加 2-5ms          │
│ 对于 P99 < 10ms 的延迟敏感服务，请谨慎评估  │
└────────────────────────────────────────────┘
```

**延迟增加实测值（不同场景）**：

| 场景 | 无 Mesh (P99) | 有 Istio (P99) | 增加 |
|------|--------------|---------------|------|
| 本地调用（同 Node） | 2ms | 4ms | +2ms (+100%) |
| 同 AZ 调用 | 5ms | 8ms | +3ms (+60%) |
| 跨 AZ 调用 | 10ms | 14ms | +4ms (+40%) |
| 跨 Region 调用 | 50ms | 55ms | +5ms (+10%) |

**运维复杂度**：

| 运维操作 | 无 Mesh | 有 Istio |
|---------|---------|----------|
| **升级 Envoy 版本** | 不涉及 | 滚动重启全部 Pod（500 Pod 约需 30-60 分钟）|
| **排查网络问题** | curl/tcpdump 直接看 | 需理解 Sidecar 路由规则，tcpdump 进出流量翻倍 |
| **配置变更** | 应用配置或平台 LB | CRD + Pilot + Envoy 三层生效链路 |
| **故障定位** | 直接看应用日志 | 需同时看 Envoy 访问日志 + 应用日志 |
| **证书管理** | 独立系统 | Citadel 自动 mTLS 证书轮换（加了一层但自动化了）|
| **健康检查** | 应用 liveness/readiness | Sidecar 启动顺序问题（Sidecar 必须先就绪）|

**升级 Sidecar 难题**：

```text
Istio Sidecar 升级流程（每次升级都是风险操作）：

1. 升级 istiod（控制面）
   ├── 无损：istiod 多副本滚动
   └── 风险：新控制面与旧 Sidecar 不兼容

2. 升级 Sidecar（数据面）
   ├── 方式一：istioctl upgrade（自动 Sidecar 注入新版本）
   │   ├── 需要滚重启所有 Pod → 所有服务在升级期间有一次重启
   │   └── 500 Pod × 60s 重启 = 8 小时+ 才能完成全面升级
   ├── 方式二：金丝雀升级（部分 Pod 先升级）
   │   ├── 降低风险，但周期更长
   │   └── 需维持新旧两个版本的 Sidecar 兼容
   └── 风险：新 Sidecar 有 bug → 全部回滚 → 又一波全量重启
```

**什么时候引入 Service Mesh？**

```
适合引入 Service Mesh 的场景：
├── 微服务数量 > 100，手动治理已到瓶颈
├── 团队有 K8s 运维能力（含 Envoy/网络专家）
├── 对延迟不敏感（P99 > 20ms 可接受）
├── 有多语言异构服务（Java + Go + Node 混合）
├── 需要零信任安全（mTLS + 细粒度鉴权）
└── 有跨集群/多云流量管理需求

不建议引入 Service Mesh 的场景：
├── 服务数 < 20，治理可通过客户端库解决
├── 团队无 K8s 专家（Istio 排错门槛极高）
├── 延迟极其敏感（P99 < 5ms）
├── 服务器资源紧张（无法承受 25%+ 的额外开销）
├── 业务快速迭代期（网格变更影响面大，增加发布阻塞风险）
└── 仅需要简单的 L4 负载均衡（现有 K8s Service 足够）
```

**网格引入的决策评分卡（1-10 分评估）**：

| 评估维度 | 权重 | 评分标准 | 你的分数 (1-10) |
|---------|------|---------|----------------|
| 服务数量 | 20% | > 100 服务 = 8-10 分，< 20 = 1-3 分 | |
| K8s 运维能力 | 20% | 有专职 SRE = 8-10 分，开发者自运维 = 1-4 分 | |
| 延迟容忍度 | 15% | P99 容忍 > 50ms = 8-10 分，< 10ms = 1-3 分 | |
| 多语言程度 | 15% | 3 种以上语言 = 8-10 分，单一语言 = 1-3 分 | |
| 零信任需求 | 10% | 有合规要求 = 8-10 分，全内网 = 1-3 分 | |
| 资源充裕度 | 10% | 有 30%+ 余量 = 8-10 分，资源紧张 = 1-3 分 | |
| 发布频率 | 10% | 低频发布 = 8-10 分，高频迭代 = 1-4 分 | |

**评分建议**：总分 ≥ 60 分 → 值得引入；总分 40-60 分 → 建议在一部分服务试点；总分 < 40 分 → 暂不引入。

## 生产案例：某出行平台的 API 网关与 Service Mesh 分级治理

### 业务背景

**公司画像**：
- 国内一线出行平台（打车 + 顺风车 + 代驾 + 租车）
- 500+ 微服务，部署在 4 个机房，3 个公有云 Region
- 日请求量 50 亿+（含内外部调用），峰值 QPS 约 80 万
- 多语言：Java（60%）+ Go（25%）+ Node.js（10%）+ Python（5%）
- 团队规模：基础架构 40 人，SRE 20 人，各业务线开发 300+ 人

### 原始架构与痛点

**原始架构（早期"网关万能"模式）**：

```
                      ┌─────────────────────────┐
外部客户端 ──────────→│    Nginx 集群 (500 台)   │
                      │    ┌─────────────────┐  │
                      │    │ 全部治理能力:     │  │
                      │    │ 认证 / 限流       │  │
                      │    │ 路由 / 协议转换    │  │
                      │    │ 服务发现         │  │
                      │    │ 熔断 / 重试       │  │
                      │    │ 负载均衡 / mTLS   │  │
                      │    │ 日志 / 监控       │  │
                      │    └─────────────────┘  │
                      └──────────┬──────────────┘
                                 │
                                 ▼
                    ┌───────────────────────┐
                    │  500+ 微服务 (K8s)     │
                    │  ┌───┐ ┌───┐ ┌───┐   │
                    │  │A  │ │B  │ │C │...│  │
                    │  └───┘ └───┘ └───┘   │
                    └───────────────────────┘
```

**痛点分析**：

| 痛点 | 表现 | 严重程度 |
|------|------|---------|
| **网关性能瓶颈** | 所有流量（外部+内部）都经过 Nginx 网关；内部服务间调用绕道网关增加 2 次网络跳转 | 🔴 严重 |
| **P99 延迟过高** | 外部请求 P99 = 800ms，内部调用因经过网关额外增加 300ms+ | 🔴 严重 |
| **单点风险** | 500 台 Nginx 集群仍扛不住峰值，限流阈值调低导致正常请求被误杀 | 🔴 严重 |
| **配置管理混乱** | 500+ 服务的限流熔断配置散落在 Nginx 配置文件中，更新需 reload | 🟡 中 |
| **能力混杂** | 网关同时处理协议转换和服务发现，逻辑耦合严重 | 🟡 中 |
| **内网流量冗余** | 服务 A → 服务 B 的调用：A → (Nginx 集群) → B，内网带宽浪费严重 | 🟡 中 |

### 架构方案设计

**目标**：
1. 网关层只处理外部流量，内部调用不再经过网关
2. P99 延迟降到 200ms 以下
3. 服务间治理能力标准化（不再每个服务各自实现）
4. 运维复杂度可控，逐步迁移

**选型过程**：

| 候选方案 | 网关 | 网格 | 复杂度 | 迁移成本 |
|---------|------|------|--------|---------|
| Nginx 优化 + 自建治理库 | Nginx | 无 | 低 | 高（需改造 500+ 服务代码）|
| **Kong 网关 + Istio 网格** | Kong (OpenResty) | Istio (Envoy) | 中 | ✅ 推荐，Sidecar 无侵入 |
| APISIX + Istio | APISIX | Istio | 中 | 性能更优但团队熟悉 Kong |
| Envoy 统一 + Istio | Envoy (入口+Sidecar) | Istio | 高 | 统一技术栈，但团队经验不足 |

**最终方案：Kong 网关 + Istio Service Mesh 分级治理**

```
外部流量 (南北向)                    内部流量 (东西向)

 客户端 → Kong 网关                    ↓
   ├── 认证 (OAuth2/JWT)             服务 A ─(Envoy Sidecar)─→ 服务 B
   ├── 限流 (全局+API级别)              │       mTLS / 熔断 / 重试
   ├── 路由 / 协议转换                 │
   ├── WAF / 跨域                    服务 C ─(Envoy Sidecar)─→ 服务 D
   └── 请求日志                        │       金丝雀 / 流量分割
       │                              │
       ▼                              ▼
   ┌─────────────┐          ┌─────────────────┐
   │ Istio 入口   │          │  Istio 网格     │
   │ Gateway     │          │  (所有服务 Pod)  │
   └──────┬──────┘          └─────────────────┘
          │                         │
          └──────────┬──────────────┘
                     ▼
           ┌──────────────────┐
           │  500+ 微服务     │
           │  (K8s + Istio)  │
           └──────────────────┘
```

### 实施细节

**第一阶段：南北向分离——Kong 网关替换 Nginx（3 个月）**

```
迁移步骤：
1. 搭建 Kong 集群（10 节点，c5.4xlarge），双活部署
2. 将 Nginx 的认证/限流/路由能力迁移到 Kong 插件
3. 配置 Kong 的 upstream 指向 K8s Service，不再做服务发现
4. 并行运行 Nginx + Kong 两周，验证路由一致性
5. 逐步切换 DNS 将流量导向 Kong
6. 下线 Nginx 集群

关键改造点：
├── 路由策略从 Nginx location → Kong Route/Service 对象
├── 认证从 Lua 脚本 → Kong OAuth2/JWT 插件
├── 限流从 ngx_http_limit_req → Kong rate-limiting 插件
└── 协议转换保留在 Kong（HTTP → gRPC-transcoding）
```

**第二阶段：东西向重构——Istio Service Mesh 接入（6 个月）**

```
迁移步骤（分批灰度）：

  首批（低风险服务，1 个月）：
  ├── 选择 10 个非核心服务（通知、短信、报表）
  ├── 启用 Istio Sidecar 注入（namespace 粒度的 label）
  ├── 验证 Sidecar 对服务的影响
  └── 配置基本的 VirtualService + DestinationRule

  二批（中等风险服务，2 个月）：
  ├── 50 个业务服务（用户查询、商品搜索）
  ├── 配置熔断、重试、超时策略
  ├── 启用 mTLS（PERMISSIVE 模式→STRICT 模式过渡）
  └── 迁移服务间调用绕过 Kong，直连 Sidecar

  三批（核心服务，3 个月）：
  ├── 100+ 核心服务（订单、支付、计价、派单）
  ├── 配置金丝雀发布、流量镜像、故障注入测试
  ├── 全面启用 STRICT mTLS
  └── 对个别旧单体服务保持传统治理，不注入 Sidecar
```

**第三阶段：关键旧单体服务保留传统治理**

```
针对历史遗留的 "old monolith"（核心计价引擎）：
├── 不注入 Istio Sidecar（老 Java 单体与 Envoy 的兼容问题）
├── 保留原有的客户端治理库（Hystrix + Ribbon）
├── 通过 Kong 网关做反向代理（外部→Kong → 单体）
└── 计划后续拆分成微服务后再接入网格

Istio 配置策略 → mTLS 绕过：
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: legacy-monolith
spec:
  host: legacy-monolith.old-ns.svc.cluster.local
  trafficPolicy:
    tls:
      mode: DISABLE  # 旧单体不启用 mTLS
```

### 关键指标前后对比

| 指标 | 改造前（Nginx + 无网格） | 改造后（Kong + Istio） | 改善幅度 |
|------|------------------------|----------------------|---------|
| **外部请求 P99 延迟** | 800ms | 120ms | **-85%** |
| **内部调用 P99 延迟** | 500ms（过网关）| 8ms（直连） | **-98.4%** |
| **网关处理流量** | 全量 50B+ 请求/天 | 仅外部 ~20B 请求/天 | **-60%** |
| **网关节点数** | Nginx 500 台 | Kong 10 台 | **-98%** |
| **新增发布周期** | 2 周/次（Nginx reload 审批流程）| 分钟级（K8s + Istio CRD） | - |
| **服务治理标准化** | 每个服务各自实现 | Istio CRD 统一管理 | 标准化 |
| **安全通信** | 内部 HTTP（明文） | 全面 mTLS（加密） | ✅ |
| **故障恢复 MTTR** | 45 分钟 | 15 分钟 | **-67%** |

**延迟改善详解**：

```text
改造前（请求经过网关）:
  客户端 → Kong → Nginx网关(500ms排队) → 内部服务
  P99 = 800ms

改造后（外部请求直连内部服务）:
  客户端 → Kong(10ms) → Istio Gateway → 内部服务
  P99 = 120ms

改造后（内部服务间调用）:
  服务A → Envoy Sidecar(2ms) → Envoy Sidecar → 服务B
  P99 = 8ms (之前 500ms 经过网关)
```

### 经验教训

**做对了的事**：

1. **分级迁移，分批灰度**：6 个月内分三批迁移，每批都有观察期，核心服务最后迁移，将风险降到最低
2. **保留旧单体特例**：不对 legacy 系统强求 Sidecar，保留传统治理库，避免了大改动带来的稳定性风险
3. **mTLS 渐进启用**：从 PERMISSIVE（同时接受 TLS 和明文）过渡到 STRICT，确保所有服务都能正常通信
4. **Kong 插件标准化**：将认证、限流等能力固化为标准插件模板，新服务接入只需声明配置

**踩过的坑**：

1. **Envoy 内存泄漏**：Istio 1.8 早期版本存在 Envoy 内存泄漏，部分高流量 Pod 的 Sidecar 内存涨到 1GB+。修复：升级到 Istio 1.10+，配置 `ENVOY_MEMORY_LIMIT=512Mi` 做硬限制
2. **Sidecar 启动顺序问题**：Pod 启动时应用容器在 Sidecar 之前就绪，导致服务注册过早。修复：配置 `holdApplicationUntilProxyStarts: true`（Istio 1.12+）
3. **网关迁移期间的流量丢失**：DNS 切换时 TTL 缓存导致部分请求路由到已下线的 Nginx。教训：DNS TTL 提前降到 60s，并使用 Kong 的健康检查自动摘除异常 upstream
4. **Istio CRD 配置扩散**：500+ 服务对应的 VirtualService / DestinationRule / ServiceEntry 数量庞大，管理混乱。修复：引入 GitOps（ArgoCD），CRD 配置代码化管理，结合自动化测试
5. **旧单体兼容问题**：老 Java 单体使用 RMI 协议，Envoy 无法代理。教训：对这类服务保持传统治理，不强制接入网格，后续拆分为微服务后再接入

**总结原则**：

```
治理能力分级：
  ├── 南北向（外部流量）：API 网关层
  │   ├── 认证、全局限流、协议转换、WAF
  │   └── 工具：Kong / APISIX
  ├── 东西向（内部流量）：Service Mesh 层
  │   ├── 服务发现、熔断、重试、mTLS、金丝雀
  │   └── 工具：Istio + Envoy
  └── 特例（存量系统）：保留传统治理
      ├── 客户端库（Hystrix / Resilience4j）
      └── 不强制 Sidecar

关键原则：
  ├── 网关不做服务发现 → 由 K8s Service + Istio 完成
  ├── 网格不做协议转换 → 由网关层完成
  ├── 避免两层同时做相同策略（如网关和 Sidecar 都限流）
  └── 先小规模验证再全面推广（网格替换不能一夜完成）
```

## 本章小结

| 要点 | 说明 |
|------|------|
| API 网关 | 统一入口、认证、限流、路由、协议转换 |
| 限流 | 令牌桶（允许突发）/ 漏桶（平滑流量）|
| 熔断 | 关闭 → 打开 → 半开 状态机 |
| 降级 | 返回兜底、关闭非核心、异步处理 |
| 重试 | 必须幂等 + 指数退避 + 有上限 |
| Service Mesh | Sidecar 代理剥离运维能力，控制面 Data Plane 分离 |
| Istio | 流量管理、安全、可观测性，K8s 上最流行的 Mesh |
