# 性能测试入门

## 不同角色看网站性能

### 用户视角

用户打开一个网站时，最关注的是响应速度：点击淘宝主页后，首页内容需要多久呈现在面前；点击提交订单按钮后需要多久返回结果。

用户通常根据响应速度的快慢来评判网站的性能。

### 开发人员视角

开发人员与用户都关注速度，这个速度实际指的是系统**处理用户请求的速度**。

开发人员难以直观评判网站性能，通常会根据当前架构及基础设施情况给出预估值，例如：

1. 项目架构是否为分布式？
2. 是否使用了缓存和消息队列？
3. 高并发业务是否有特殊处理？
4. 数据库设计是否合理？
5. 系统中的算法是否需要优化？
6. 系统是否存在内存泄漏问题？
7. 项目使用的 Redis 缓存容量多大？服务器性能如何？使用机械硬盘还是固态硬盘？
8. 其他潜在因素……

### 测试人员视角

测试人员使用性能测试工具进行测试，通常生成包含以下重要指标的报告：

1. 响应时间
2. 请求成功率
3. 吞吐量
4. 其他相关指标

### 运维人员视角

运维人员倾向于根据基础设施和资源利用率来判断网站性能，例如服务器资源使用是否合理、数据库资源是否存在滥用情况。

## 性能测试注意事项

多数性能测试文章侧重讲解测试方法与指标，但容易忽略以下关键前提。

### 了解系统的业务场景

**性能测试之前，需先深入了解当前系统的业务场景。** 对业务了解不够深刻，容易犯测试方向偏执的错误，从而忽略某些更需要性能测试的环节。例如：系统为用户提供发送邮件的功能，每天处理上万次发邮件请求。若直接对邮箱发送接口进行测试，可能发现这并不是性能瓶颈——大量用户同时使用系统，用户管理模块承受的压力可能更大。

### 历史数据非常有用

系统遗留的历史数据非常重要。通过历史数据可以初步判断哪些接口调用频繁、哪些服务压力最大，从而针对这些关键点进行更细致的性能测试与分析。

这些关键点如同系统的短板，优化后能为系统带来质的提升。

## 常见性能指标

### 响应时间

**响应时间（RT，Response-time）是用户发出请求到收到系统处理结果所需的时间。**

RT 是一个直观且重要的指标，其数值直接反映系统处理用户请求的速度。

### 并发数

**并发数指系统同时能够处理的请求数量，即可同时服务的用户数。**

并发数反映系统的负载能力。

### QPS 和 TPS

- **QPS（Queries Per Second）**：服务器每秒可以执行的查询次数
- **TPS（Transactions Per Second）**：服务器每秒处理的事务数（一个事务可理解为从客户发出请求到收到服务器响应的完整过程）

QPS 与 TPS 的区别在于：对一个页面的一次访问，形成一个 TPS；但一次页面请求可能产生多次对服务器的请求，这些请求可计入 QPS。例如，访问一个页面请求服务器 2 次，一次访问产生 1 个 T，产生 2 个 Q。

### 吞吐量

**吞吐量指系统单位时间内处理的请求数量。**

吞吐量与请求对系统资源的消耗紧密相关。请求对系统资源消耗越多，系统吞吐能力越低，反之则越高。

TPS、QPS 都是吞吐量的常用量化指标。

- **QPS（TPS）** = 并发数 / 平均响应时间（RT）
- **并发数** = QPS × 平均响应时间（RT）

## 系统活跃度指标

### PV（Page View，页面浏览量）

在一定统计周期内，用户每打开或刷新一个页面就记录 1 次，多次打开或刷新同一页面则累计计算。PV 从页面被打开/刷新的次数角度进行统计。

### UV（Unique Visitor，独立访客）

统计 1 天内访问某站点的独立用户数。1 天内同一访客多次访问网站，仅计算为 1 个独立访客。UV 从用户个体的角度进行统计。

### DAU（Daily Active User，日活跃用户）

统计单日内活跃的用户数量。

### MAU（Monthly Active Users，月活跃用户）

统计单月内活跃的用户数量。

### 计算示例

某网站 DAU 为 1200 万，用户日均使用时长为 1 小时，RT 为 0.5 秒，求并发量和 QPS。

| 参数 | 计算公式 | 结果 |
|------|----------|------|
| 平均并发量 | DAU（1200 万）× 日均使用时长（1 小时，3600 秒）/ 一天的秒数（86400）= 1200 万 / 24 | ≈ **50 万** |
| 真实并发量（考虑低峰期） | DAU（1200 万）× 日均使用时长（1 小时，3600 秒）/（一天秒数 - 低峰时段，假设 8 小时 / 57600 秒）= 1200 万 / 16 | ≈ **75 万** |
| 峰值并发量 | 平均并发量 × 6 | ≈ **300 万** |
| QPS | 真实并发量 / RT = 75 万 / 0.5 | ≈ **150 万 / 秒** |

## 性能测试分类

### 性能测试

性能测试方法通过测试工具模拟用户请求，目的是验证系统性能是否满足要求。即在特定运行条件下验证系统的能力状态。

性能测试需在对系统性能已有了解的前提下进行，并有明确的性能指标。

### 负载测试

对被测系统持续加大请求压力，直到服务器某个资源达到饱和（如缓存不足或响应时间不达标）。负载测试旨在找出系统上限。

### 压力测试

不考虑系统资源使用情况，对系统持续加大请求压力，直到服务器崩溃无法继续提供服务。

### 稳定性测试

模拟真实场景，给系统施加一定压力，观察业务能否稳定运行。

## 常用性能测试工具

### 后端常用工具

在涉及系统性能的面试中，面试官常会问：**你是如何进行性能测试的？**

推荐以下常用性能测试工具：

1. **JMeter**：Apache 基金会开发的 Java 性能测试工具
2. **Gatling**：基于 Scala 开发的高性能服务器性能测试工具
3. **ab（Apache Bench）**：Apache 旗下的轻量级测试工具，使用方便

### 前端常用工具

1. **Fiddler**：抓包调试工具，可修改请求数据甚至服务器返回数据，是 Web 调试利器
2. **HttpWatch**：HTTP 请求信息录制工具

## 常见的性能优化策略

性能优化前需要对请求经历的各个环节进行分析，排查可能出现性能瓶颈的地方，定位问题。

以下为性能优化时值得自问的一些问题：

1. 系统是否需要引入缓存？
2. 系统架构本身是否存在问题？
3. 系统是否存在死锁？
4. 系统是否存在内存泄漏？（Java 自动内存回收虽方便，但代码编写不当仍会导致内存泄漏）
5. 数据库索引使用是否合理？
6. 其他潜在优化点……
