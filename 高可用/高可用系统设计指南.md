# 高可用系统设计指南

## 什么是高可用？可用性的判断标准是什么？

高可用（High Availability，HA）描述的是一个系统在大部分时间内保持可用、持续提供服务的能力。高可用代表系统即使在发生硬件故障或者系统升级的时候，服务仍然是可以访问的。

一般情况下，使用**多少个 9** 来评判一个系统的可用性。例如，99.9999% 表示该系统在所有的运行时间中只有 0.0001% 的时间是不可用的，这是极高可用的水平。当然，如果系统可用性较差，可能连一个 9 都达不到。

除此之外，系统的可用性还可以用某功能的失败次数与总的请求次数之比来衡量。例如，对网站请求 1000 次，其中有 10 次请求失败，那么可用性就是 99%。

## 哪些情况会导致系统不可用？

1. **黑客攻击**
2. **硬件故障**，例如服务器损坏
3. **并发量/用户请求量激增**，导致整个服务宕机或部分服务不可用
4. **代码缺陷**，例如内存泄漏或其他问题导致程序崩溃
5. **关键组件故障**，例如 Nginx 或数据库突然不可用
6. **自然灾害或人为破坏**
7. ……

## 有哪些提高系统可用性的方法？

### 注重代码质量，测试严格把关

代码质量是系统可用性的源头。常见问题如内存泄漏、循环依赖等都严重损害系统可用性。业界常讨论限流、降级、熔断等手段，但从代码质量这个源头把关才是首先要做好的基础工作。提高代码质量的有效手段包括 **Code Review** 和自动化测试。Code Review 虽然每天多花费约一小时，但能显著提升代码质量，降低线上故障风险。

### 使用集群，减少单点故障

以 Redis 为例：如何保证 Redis 缓存的高可用？答案是**使用集群，避免单点故障**。当只使用一个 Redis 实例作为缓存时，该实例一旦宕机，整个缓存服务可能就无法工作。使用集群后，即使一台 Redis 实例发生故障，集群会通过哨兵机制或集群协议自动切换，由其他实例快速接替服务。

### 限流

流量控制（Flow Control），其原理是监控应用流量的 QPS（Queries Per Second）或并发线程数等指标，当达到指定的阈值时对流量进行控制，以避免被瞬时的流量高峰冲垮，从而保障应用的高可用性。——来自 [alibaba-Sentinel](https://github.com/alibaba/Sentinel) 的 Wiki。

### 超时和重试机制设置

一旦用户请求超过某个时间未得到响应，就应抛出异常。这是非常重要的——很多线上系统故障都是因为没有进行超时设置或者超时设置方式不当导致的。在读取第三方服务时，尤其适合设置超时和重试机制。大多数 RPC（Remote Procedure Call）框架都自带超时重试配置。不进行超时设置可能导致请求响应速度变慢，甚至导致请求堆积，进而让系统无法再处理新的请求。重试次数一般设为 3 次，更多次的重试没有额外好处，反而会加重服务器压力（部分场景下使用失败重试机制可能不太适合）。

### 熔断机制

除超时和重试机制外，熔断机制也很重要。熔断机制是指系统自动收集所依赖服务的资源使用情况和性能指标，当所依赖的服务恶化或者调用失败次数达到某个阈值时，系统迅速失败，让当前服务立即切换依赖其他备用服务。常用的流量控制和熔断降级框架包括 Netflix 的 **Hystrix** 和阿里巴巴的 **Sentinel**。

### 异步调用

异步调用不需要等待最终结果，用户请求完成后可立即返回响应，具体处理可以后续再做。秒杀场景中异步调用应用广泛。但使用异步之后，可能需要**适当修改业务流程进行配合**，例如：

> 用户在提交订单后，不能立即返回"订单提交成功"，需要在消息队列的订单消费者进程真正处理完该订单之后，甚至出库后，再通过电子邮件或短信通知用户订单成功。

除了在程序中实现异步之外，还常使用消息队列，消息队列可以：

- 通过异步处理提高系统性能（削峰填谷、减少响应时间）
- 降低系统耦合性

### 使用缓存

对于并发量较高的系统，如果单纯直接使用数据库，大量请求可能直接压垮数据库。使用缓存来存储热点数据，由于缓存放于内存中，访问速度远快于磁盘 I/O。常见的缓存中间件包括 Redis 和 Memcached。

### 其他

- **核心应用和服务优先使用更好的硬件**
- **监控系统资源使用情况，增加报警设置**
- **注意备份，必要时回滚**
- **灰度发布**：将服务器集群分成若干部分，每天只发布一部分机器，观察运行稳定无故障后，第二天继续发布下一部分，持续数天完成全量发布。若期间发现问题，只需回滚已发布的部分服务器
- **定期检查/更换硬件**：若未使用云服务，定期对硬件进行检查，对需要更换或升级的硬件及时处理
- ……
