# 冗余设计详解

## 概述

冗余设计是保证系统和数据高可用的**最常用的手段**。

对于**服务**来说，冗余的思想就是相同的服务部署多份。如果正在使用的服务突然挂掉，系统可以很快切换到备份服务上，大大减少系统的不可用时间，提高系统的可用性。

对于**数据**来说，冗余的思想就是相同的数据备份多份，从而简单地提高数据的安全性。

## 典型应用方案对比

高可用集群（High Availability Cluster，简称 HA Cluster）、同城灾备、异地灾备、同城多活和异地多活是冗余思想在高可用系统设计中最典型的应用。下表从多个维度对比这五种方案：

| 方案 | 服务冗余 | 地域冗余 | 多活（同时对外服务） | 适用场景 |
|------|---------|---------|-------------------|---------|
| **高可用集群** | ✅ 多份部署 | ❌ 无地域概念 | ❌ 主备切换 | 单机房内服务高可用 |
| **同城灾备** | ✅ 多份部署 | ✅ 同城不同机房 | ❌ 备用不处理请求 | 防止机房级故障（停电、火灾） |
| **异地灾备** | ✅ 多份部署 | ✅ 异地不同机房 | ❌ 备用不处理请求 | 防止地域级灾害 |
| **同城多活** | ✅ 多份部署 | ✅ 同城不同机房 | ✅ 所有站点对外服务 | 充分利用系统资源，提高并发 |
| **异地多活** | ✅ 多份部署 | ✅ 异地不同机房 | ✅ 所有站点对外服务 | 应对大规模自然/人为灾害 |

> 高可用集群单纯是服务的冗余，并没有强调地域。同城灾备、异地灾备、同城多活和异地多活实现了地域上的冗余。
>
> 同城和异地的主要区别在于机房之间的距离。异地通常距离较远，甚至是在不同的城市或者国家。

### 灾备与多活的核心区别

- **灾备（主备模式）**：备用站点不处理请求，资源利用率低，但架构相对简单
- **多活（多活模式）**：所有站点同时对外提供服务，资源利用率高，但架构复杂度大幅上升

异地多活主要是为了应对突发状况，如火灾、地震等自然或人为灾害。和传统的灾备设计相比，多活最明显的改变在于所有站点都在同时工作。

## 故障转移

光做好冗余还不够，必须要配合上**故障转移**才可以。所谓故障转移，就是实现不可用服务快速且自动地切换到可用服务，整个过程不需要人为干涉。

### 故障转移的核心流程

一个完整的故障转移通常包含以下阶段：

| 阶段 | 说明 | 关键技术 |
|------|------|---------|
| **故障检测** | 发现节点不可用 | 心跳检测、健康检查探针、超时阈值 |
| **节点隔离** | 隔离故障节点，防止产生错误响应 | 断路器（Circuit Breaker）、优雅摘流 |
| **选主/切换** | 从存活的节点中选出新的主节点 | 选举算法（Raft、Paxos、Zab）、VIP 漂移 |
| **状态同步** | 新主节点加载/恢复最新状态 | 日志回放、状态复制、增量同步 |
| **路由更新** | 将流量导向新主节点 | 虚拟 IP 漂移、DNS 更新、配置中心通知 |

### 健康检查机制

健康检查是故障转移的**第一道防线**，用于持续监控节点的存活状态。常见的健康检查方式包括：

| 方式 | 原理 | 典型实现 |
|------|------|---------|
| **心跳检测（Heartbeat）** | 节点间定时发送心跳信号，连续 N 次未收到则判定为故障 | Redis Sentinel 的 PING/PONG、Keepalived 的 VRRP 广播 |
| **应用层健康探针** | 请求约定的 HTTP/HTTPS 端点，检查返回状态码 | Spring Boot Actuator 的 `/actuator/health`、Kubernetes 的 liveness/readiness probe |
| **TCP 端口检测** | 尝试建立 TCP 连接，失败则标记异常 | 负载均衡器的后端健康检查 |
| **被动检测（超时/重试）** | 客户端请求超时后触发重试，累计异常次数超过阈值判定为故障 | gRPC 的重试策略、Hystrix 断路器 |

### 选举算法

在有状态服务（如数据库、缓存）的故障转移中，存活的节点需要通过选举算法选出一个新的主节点（Leader）。常见的选举算法有：

#### Raft

Raft 是目前应用最广泛的共识算法之一，以**易于理解**著称。其选举流程如下：

1. 节点初始均为 **Follower**（跟随者）
2. 若 Follower 在 **选举超时**（通常是 150~300ms 随机值）内未收到 Leader 的心跳，则变为 **Candidate**（候选者）
3. Candidate 向其他节点发起投票请求
4. 获得**多数派（quorum，即 N/2 + 1）**投票的节点成为新的 Leader
5. Leader 定期发送心跳维持权威

> 典型应用：etcd（Kubernetes 的存储后端）、Consul、TiKV

#### Paxos

Paxos 是分布式共识的开山之作，比 Raft 更早提出，但理解门槛较高。其核心是两阶段提交（Prepare → Accept），保证在节点故障时仍能达成一致。

> 典型应用：Google Chubby、Apache ZooKeeper（基于 Zab 协议，借鉴 Paxos 思想）

#### Zab（ZooKeeper Atomic Broadcast）

ZooKeeper 使用的选举协议，采用**领导者和追随者**模式。通过 **Fast Leader Election** 算法快速选主，支持动态加入和退出。

### 虚拟 IP（VIP）漂移

VIP 漂移是无状态服务故障转移的常见手段。主备节点共享一个虚拟 IP，主节点正常时持有 VIP 并处理请求；主节点故障后，备用节点获取 VIP 所有权，对外 IP 不变，客户端无感知。

> 典型应用：Keepalived（基于 VRRP 协议）、云平台的浮动 IP

### Redis Sentinel 详解

在哨兵模式的 Redis 集群中，如果 Sentinel（哨兵）检测到 master 节点出现故障，会自动进行故障转移，将某一台 slave 升级为 master，确保整个 Redis 系统的可用性。

在哨兵模式的 Redis 集群中，故障转移流程如下：

1. **主观下线**：Sentinel 向 master 发送 PING，若超过 `down-after-milliseconds` 未收到 PONG 回复，则标记为主观下线（sdown）
2. **客观下线**：若有多个 Sentinel 实例（通常需要 quorum 个）也认为 master 不可达，则标记为客观下线（odown）
3. **Leader Sentinel 选举**：Sentinel 集群通过 Raft 类似的算法选出一个 Leader Sentinel 负责执行故障转移
4. **Slave 筛选与升级**：从存活的 slave 中选出一个最合适的（优先级最高、复制偏移量最大），执行 `SLAVEOF NO ONE` 将其升级为 master
5. **重新配置**：其他 slave 执行 `SLAVEOF new_master`，开始复制新 master

### Nginx + Keepalived 详解

Nginx 可以结合 Keepalived 来实现高可用。如果 Nginx 主服务器宕机，Keepalived 会自动进行故障转移，备用 Nginx 主服务器升级为主服务。这个切换对外是透明的，因为系统使用的是虚拟 IP，虚拟 IP 在故障转移过程中不会改变。

Keepalived 通过 VRRP（Virtual Router Redundancy Protocol，虚拟路由冗余协议）实现高可用：

1. **VRRP 组**：主备 Nginx 绑定同一 VRRP 实例，共享虚拟 IP
2. **健康检查**：Keepalived 定期执行自定义脚本检测 Nginx 进程是否存活（如 `curl http://localhost/health`）
3. **主备切换**：若脚本连续 N 次失败，Keepalived 降低本机优先级并停止发送 VRRP 通告；备机在超时后接管 VIP，开始处理请求
4. **状态同步**：备机接管后，Nginx 重新读取配置文件，对客户端透明
